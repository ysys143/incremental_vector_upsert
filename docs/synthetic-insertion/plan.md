# 삽입에 따른 인덱스 품질 변화: 로컬 후속 실험 계획

상태: 계획 작성 완료, 구현·실험 미실행. 기존 전체 계획과 1차 파일럿 원시 증거는 보존한다.

## 1. 연구 질문과 판정

목표는 **어떤 신규 벡터를 얼마나, 어떤 순서와 단위로 삽입했을 때 검색 품질이
변하며, 그중 어느 부분이 현재 데이터의 검색 난도와 증분 구축 경로에 관련되는지**
분리하는 것이다. 배치 분할만을 연구 질문으로 삼지 않는다.

사용자는 로컬에서 결과를 검토하고 이후 실제 데이터·다른 DB·클라우드 실험의
조건을 결정한다. 이번 단계는 PostgreSQL+pgvector HNSW 및 Qdrant HNSW의 합성
데이터 실험이다. 삭제·동일 ID 교체·필터·다른 제품은 보존한 전체 연구의 후속 단계다.

시점 t의 생존 데이터 D_t에 대해 동일한 exact oracle, 질의, 검색 설정으로 다음을 구한다.

- `R_inc(t)`: 증분 인덱스의 Recall@10·100. 실제 삽입 전후 품질 곡선이다.
- `R_fresh(t)`: 같은 D_t로 새로 구축한 인덱스의 Recall@10·100.
- `history_gap(t) = R_inc(t) - R_fresh(t)`: 현재 데이터·설정이 같을 때의 차이.
- `path_gap = R_inc(one_wave, final) - R_inc(five_waves, final)`:
  초기 인덱스·최종 데이터·벡터 순서까지 동일한 두 경로의 차이.

전체 값과 기존·신규·경계 질의 집단의 값을 각각 보고한다. 삽입 전후 차이만으로
구조적 열화를 판정하지 않는다. fresh 차이에도 구축 난수·구축 순서·유지보수 경로가
영향을 주므로 알고리즘의 영구 손상을 단정하지 않는다.

예비 경고 기준은 집단별 또는 전체 history_gap이 -0.5%p 이하이며, 3개 데이터 seed 중
2개 이상에서 재현되고 최종 fresh 반복의 변동 범위로 설명되지 않는 경우다.
이 기준은 검출할 효과 크기의 기본값이며 동등성 검정이나 제품 우열의 기준이 아니다.
작은 표본·천장 효과·구축 편차 때문에 구분하지 못하면 INCONCLUSIVE로 표시한다.

## 2. 데이터·경로와 실험표

### 공통 입력

- 초기 N=10,000, 128차원 float32, squared L2 oracle, 평가 seed=11·29·47.
- 초기 데이터는 균등한 두 Gaussian 군집이다. 표준편차 1, 회전 전 중심은
  첫 축의 ±`2*sqrt(128)`, 나머지 좌표는 0이다. seed별 고정 직교 회전을 모든 입력에 공유한다.
- 신규 풀은 최대 10,000개를 한 번 생성한다. 신규/기존 ID와 벡터는 경로 간 동일하다.
  최종 집합 일치는 ID·float32 벡터 해시로 검증한다.
- 상대 삽입량은 초기 N 대비 10%(1,000개)와 100%(10,000개)다.
- 분할은 한 번 또는 동일 크기 5회다. 핵심 쌍은 `10K+10K`와 `10K+2K*5`다.
  작은 비율에서는 `10K+1K`와 `10K+200*5`를 비교한다.
- 기본 순서는 seed로 고정한 무작위 순서다. 한 번·다섯 번 경로는 동일한 순서열의
  경계만 바꾼다. 여러 요청으로 자동 분할해서 한 번 조건을 가장하지 않는다.

### 신규 집단의 네 조건

초기 데이터의 median 20-NN 거리를 r로 놓고 다음 fixture를 만든다.

| 조건 | 생성 방법 | 확인할 차이 |
|---|---|---|
| IID | 초기 데이터와 같은 두 군집에서 독립 추출 | 분포 이동 없는 삽입·규모 증가 |
| 근거리 이동 | IID 신규 풀을 두 번째 축으로 0.25r 이동 | 기존 영역과 중첩되는 변화 |
| 분리된 신규 집단 | IID 신규 풀을 두 번째 축으로 3r 이동 | 기존 영역에서 떨어진 신규 모드 |
| 연결 영역 | 두 초기 중심 사이에서 균등하게 중심을 뽑고 표준편차 1의 Gaussian 잡음 추가 | 기존 군집 사이의 연결 변화 |

모든 기하 변환을 회전 전 좌표에서 수행한 뒤 공통 직교 회전을 적용한다.
거리·밀도·연결성은 이 생성만으로 독립 통제됐다고 주장하지 않는다. 생성 목표와
실현값을 구분하고, 실제로 다음을 측정한다.

- 신규/기존 비율, 신규→기존 최근접 거리와 기존 내부 최근접 거리의 비.
- 20-NN 거리의 중앙값·분위수 및 k=20 기반 LID 추정의 집단별 분포.
- 고정 bandwidth의 RBF-MMD: seed별 D0 표본으로 bandwidth를 고정하고,
  각 집단에서 최대 1,024개를 결정적으로 표본 추출한다.
- exact 20-NN 그래프를 대칭화한 연결 성분 수·최대 성분 비율,
  기존/신규 사이의 이웃 비율과 해당 cut의 conductance.

그래프 진단은 D0와 각 고유 최종 데이터에서만 계산하고 경로 간 재사용한다.
이는 **데이터의 exact kNN 구조**이며 제품 내부 ANN 그래프를 관측한 값이 아니다.
IID의 실현 분포, 분리 조건의 낮은 교차 이웃 비율, 연결 영역의 연결 성분 변화가
생성 의도와 일치하는지 DB 실행 전에 검사한다. 의도와 다르면 fixture 준비 실패로
멈추며 ANN 결과를 보고 fixture를 고르지 않는다.

### 질의 집단

데이터와 별도로 기존 분포·신규 분포·경계 영역에서 각 200개, 총 600개를 생성한다.
질의는 삽입할 문서 벡터와 일치하지 않는다. 경계 질의는 두 영역 사이의 독립 후보에서
최종 최대 신규 풀과 D0에 대한 최근접 거리 비가 0.8~1.25인 후보를 선택한다.
후보 생성 상한 20,000개에서 200개를 확보하지 못하면 fixture 준비 실패다.

geometry·seed별 같은 질의를 모든 삽입 비율·시점·경로에서 유지한다. 경계 집단은
최대 삽입량을 기준으로 정의했음을 명시하고, 각 시점의 실제 정답 이웃 구성도 기록한다.
미래 신규 분포의 질의 역시 삽입 전에는 D0만 대상으로 정답을 계산한다.
전체 점수는 세 집단의 동일 가중 평균이며 실제 서비스 질의 비율이라고 해석하지 않는다.

### 단계별 실험표

| 단계 | 조건 | 추가 경로 수 |
|---|---|---:|
| A: 크기·기본 경로 | 2 DB × 3 seed × IID × 삽입 비율 2개 × 분할 2개 | 24 |
| B: 신규 집단 특성 | 2 DB × 3 seed × 나머지 geometry 3개 × 비율 2개 × 분할 2개 | 72 |
| C: 삽입 순서 | 2 DB × 3 seed × 분리·연결 geometry 2개 × 비율 100% × 분할 2개 | 24 |
| D: 중간 관찰 영향 | 2 DB × 3 seed × IID·분리 geometry 2개 × 비율 100% × 5회 분할 | 12 |
| 합계 | 같은 초기 상태를 공유하는 대응 경로이며 132개 독립 표본이라는 뜻은 아님 | **132** |

C는 기본 무작위 순서와 같은 최종 데이터를 사용한다. 분리 조건은 신규 군집별 연속
삽입, 연결 조건은 초기 두 중심을 잇는 축을 따라 순차 삽입한다. 각 조건 안에서는
한 번·다섯 번 경로가 동일 순서를 공유한다.

A~C는 매 wave 후 쓰기·인덱싱 대기와 품질 측정을 한다. 한 번 경로는 초기·최종만,
다섯 번 경로는 초기와 각 wave를 측정한다. 따라서 주 비교는 배치 크기와 중간 대기를
포함한 경로 비교다. 배치 크기만의 순수 효과라고 부르지 않는다.
D는 5회 요청 사이에 완료 응답만 받고 다음 요청을 보낸다. 중간 상태 조회·품질 측정·
인덱싱 대기 없이 초기·최종만 측정해 관찰 및 대기 정책의 영향을 따로 확인한다.
API 배치와 실제 그래프 편입·segment 구축·merge 단위는 같다고 가정하지 않는다.

## 3. 대조군·튜닝·검색 경로

### 같은 초기 인덱스에서 분기

DB·데이터 seed별 초기 인덱스를 한 번 구축한 뒤 정상 종료된 전용 데이터 볼륨을
복제해 각 경로를 시작한다. 라이브 볼륨 복사나 pg_dump로 인덱스를 다시 만드는
방식은 쓰지 않는다. 동일 이미지·설정·초기 파일 해시, 복원 후 ID·벡터·인덱스 상태를
검증한다. 복원 과정에 재구축이 있으면 초기 상태 동등성 실패다.

PostgreSQL은 클러스터 전체를 정상 종료 후 복사한다.
[공식 파일 시스템 백업 조건](https://www.postgresql.org/docs/17/backup-file.html).
Qdrant도 정상 종료·저장 완료 후 전용 storage 전체를 복제한다.
고정 Qdrant 이미지의 정상 SIGTERM 종료 코드는 실제 검사에서 143이었다. flush 주기+1초
동안 추가 쓰기 없이 기다리고, graceful shutdown 로그·OOM/강제 종료 여부를 확인한다.
복원 시작 전 전체 파일 해시와 시작 후 nonempty segment UUID·HNSW 그래프 파일 해시를
함께 검사한다. 143이라는 값만으로 정상 종료나 동일 초기 그래프를 인정하지 않는다.
기본 상태 원본은 읽기 전용으로 보존하고 한 번에 복제본 하나만 실행한다.

### 모든 고유 시점에 fresh 대조군

고유 D_t마다 전체 데이터를 적재한 뒤 인덱스를 새로 구축한다. 새 임의 순서로
매번 바꾸지 않고 seed별 고정 canonical 순서를 사용한다. 증분과 동일한 설정과
자원 한도를 적용한다. 초기 그래프의 clone은 fresh 대조군으로 사용하지 않는다.

fresh는 데이터·벡터·canonical 순서·DB 이미지·설정 해시가 같은 경우에만 재사용한다.
최종 데이터 8종(geometry 4 × 비율 2)은 각각 총 3회 fresh 구축해 내부 구축 편차를
관찰한다. 중간 시점은 1회로 제한하고 해당 비교의 불확실성을 표시한다.

계획상 품질 측정 개수:

- 증분 경로 checkpoint: A 96 + B 288 + C 96 + D 24 = **504**.
- 고유 중간/최종 데이터 상태: 기본 40 + C의 추가 중간 상태 8 = 48종/DB·seed.
- fresh 기본 측정: 48 × 2 DB × 3 seed = 288.
- 최종 fresh 추가 반복: 8 × 2회 × 2 DB × 3 seed = 96.
- fresh 합계 **384**, 증분 포함 총 **888**. 스모크·튜닝·fixture 진단은 별도다.

중간 시점 fresh는 다른 전용 복제본에서 실행한다. 대조군 계산·정답 계산으로
본래 증분 경로의 진행을 추가로 지연시키지 않도록 해당 wave의 품질 측정 후
증거를 저장하고, 경로 완료 뒤 대조군 작업을 수행한다.
모든 D_t와 고정 질의의 exact top-100은 이벤트 원장으로 미리 계산해 입력 해시와
함께 저장한다. 실행 중에는 해당 D_t의 해시 일치를 확인해 읽으며, 다른 시점 정답을
전용하지 않는다. DB readback은 별도 원장 검증으로 수행한다.

### DB별 튜닝

기존 파일럿의 승자 설정을 최적값으로 재사용하지 않는다. 평가와 분리한 seed=7로
D0 및 네 geometry의 최대 삽입량 fresh 상태를 튜닝한다. 튜닝 질의는 상태당 200개이며
평가 질의와 분리한다. 두 DB에 같은 자원 한도와 탐색 상한을 적용한다.

- 구축 후보 `(M, efConstruction)=(16,100),(32,200)`.
- 검색 ef=100·128·256. 두 Recall 목표를 모든 튜닝 상태에서 만족하는 후보가 없을
  때만 ef=512를 추가한다. 이후도 미달이면 QUALITY_TARGET_UNMET로 멈춘다.
- Recall@10·100 ≥0.95인 후보 중 상태별 중앙 검색 지연의 평균이 가장 낮은 구성을
  DB별 하나 선택한다. 모든 평가 seed·geometry·경로에서 동결한다.
- 초기 적재는 PostgreSQL COPY 후 인덱스 생성·ANALYZE, Qdrant는 bulk 적재 후
  인덱싱을 사용한다. 초기 전송 배치 100·1000은 별도로 비교한다.
- 증분 wave는 실험 변수를 보존하도록 한 번의 COPY/커밋 또는 한 번의 batch upsert로
  보낸다. 기존 adapter의 자동 chunk 분할을 이 경로에서는 제거한다. 최대 요청의
  실제 직렬화 크기를 스모크에서 확인하고 서버 제한 초과 시 실패시킨다.
- `wait=true`, WAL·내구성 설정·정상 optimizer는 유지한다. 데이터가 추가될 때마다
  검색 ef를 올리거나 평가 결과를 보고 설정을 바꾸지 않는다.

여기서 최적은 공개한 후보·자원 내 선택을 의미한다. API 호출/커밋 단위를 바꾼 실험을
제품 내부 ANN batch 크기를 직접 제어한 실험으로 표현하지 않는다.

### 순차 스캔·exact fallback 배제

PostgreSQL은 현재 추가한 검증을 유지한다. 모든 검색 연결에서 `enable_seqscan=off`,
`enable_indexscan=on`, `hnsw.iterative_scan=strict_order`를 적용한다. 매 검색 전 같은
SQL의 EXPLAIN에서 지정 HNSW만 허용하고, checkpoint의 EXPLAIN ANALYZE로 실제
실행도 확인한다. 다른 scan·sort·설정 변경은 측정 실패다. 검사 비용은 검색 지연
타이밍 밖으로 분리하되, 검증한 SQL을 동일 private 연결에서 즉시 실행한다.
동시 DDL을 금지하며 연결 재시작·스키마 변경 시 이전 검증을 재사용하지 않는다.

Qdrant는 `exact=false`, full_scan_threshold=10KiB와 인덱스 상태 확인에 더해
측정 전후 상세 telemetry의 `unfiltered_hnsw.count`·`unfiltered_plain.count`를 대조한다.
[1.17 공식 telemetry 스키마](https://api.qdrant.tech/v-1-17-x/api-reference/service/telemetry?explorer=true).
정답 검증·warmup 후 카운터를 읽고 평가 검색만 실행한 뒤 다시 읽는다.
비어 있지 않은 segment에서 plain 증가가 0이고 HNSW 증가가 평가 질의 수 이상이며
오류 증가가 없어야 ANN 측정으로 인정한다. 카운터는 segment 단위라 질의 수와
정확히 같다고 요구하지 않는다.

측정 중 segment 집합/카운터가 교체되거나 필수 telemetry 구조가 없으면
UNVERIFIED로 기록한다. 데이터 누락을 숨기는 indexed_only로 대체하지 않는다.
구현 사전 검증에서 Qdrant 1.17.1은 상세도 4에서 segment 정보를 제공하고,
사용하지 않은 개별 통계 멤버는 `OperationDurationStatistics::is_empty`에 의해
직렬화에서 생략함을 공식 소스와 실제 양성 대조군으로 확인했다.
[고정 버전 직렬화 정의](https://github.com/qdrant/qdrant/blob/v1.17.1/lib/segment/src/telemetry.rs).
따라서 완전한 segment/index 구조·UUID·고정 버전·HNSW 증가가 확인된 경우에만
이 명시적 생략을 0-event로 해석한다. segment/index 구조 누락·버전 불일치·카운터
감소는 이 예외에 해당하지 않는다. plain뿐 아니라 unfiltered_exact 증가도 거부한다.
스모크에서 카운터가 실제 경로를 구분하는지 plain 양성 대조군으로 먼저 검증한다.
해당 버전에서 증명이 안 되면 Qdrant ANN-only 단계는 BLOCK이며 전체 완료가 아니다.
의도적인 plain 양성 대조군은 검사 전용 데이터이며 품질 비교 표에서 제외한다.

기본 인덱싱 대기는 최대 120초, 0.5초 간격으로 상태를 수집한다. PostgreSQL commit과
Qdrant 인덱싱 완료는 다른 사건이므로 쓰기 확인·검색 가시성·ANN 준비 시간을 각각
기록한다. 원장 조회·독립 exact oracle의 전체 데이터 읽기는 ANN 검색과 구분한다.

## 4. 구현·검증·실행 순서

### 필요한 변경

- 입력 생성기를 기존/신규 집단·기하 조건·질의 집단·순서 생성으로 분리한다.
  현재 `n/rounds`만 가진 설정에 삽입 비율·wave 수·순서·대기 정책을 추가한다.
- 어댑터에 wave 전체 삽입, 초기 상태 복제/복원, ANN 준비 확인, 검색 경로 검증,
  검증과 분리한 검색 실행을 추가한다. 실제 요청 수·건수·payload bytes를 남긴다.
- 실행기는 cell manifest와 완료 원장으로 재개한다. 상태는 NOT_STARTED/RUNNING/
  PASS/FAIL/UNVERIFIED를 구분하고 완료 cell을 다시 실행하지 않는다.
  기존 결과·실패 로그·소스 스냅샷을 수정하지 않는다.
- 대조군·oracle·기하 진단은 검증된 content hash로만 재사용한다. 결과에는 모든
  설정·상태·질의 집단·per-query ID·거리 또는 순위·latency와 해시를 보존한다.

사용자의 후속 요청으로 just-dag-it을 검토한 결과, 132개 경로와 대조군의 재개·시간
한도·독립 정리를 관리하기 위해 Dagster를 사용한다. fixture 검증·튜닝·초기 snapshot·
증분 경로·fresh 대조군을 각각 partitioned asset으로 나누고 명시적 partition mapping으로
의존성을 연결한다. 입력/oracle 준비는 고정 입력 생성 명령으로 수행한 뒤 fixture asset이
해시와 내용을 검증한다. 준비를 native materialization으로 가장하지 않는다.
완료는 성공한 native run ID·동일 실행 scope·결과 파일/ack 해시가 모두 있어야 인정한다.
Dagster 1.13.26은 로컬 캐시의 Python 3.13 가상환경에서 실행하고 실제 측정은 기존
Python 3.14·NumPy 2.5.2 런타임으로 호출한다. 상시 daemon·클라우드·추가 에이전트
worker는 사용하지 않는다. 단일 controller가 한 번에 한 partition을 materialize하며,
별도 watchdog이 controller 사망과 deadline 초과 후 owned 자원을 정리한다.
자동 변경 재전송·자동 재튜닝은 하지 않는다. 실패 원인 진단은 현재 세션이 담당한다.

### 실행 단계

1. 선행자료의 주장·원문 URL·평가 정의를 검증한다. 붙여 받은 참조 대화는 요구사항
   자료로 사용하되, 링크가 없는 연구 수치를 검증된 수치로 인용하지 않는다.
   정적 최종 정답/적재율 보정 recall과 현재 D_t의 exact recall을 구분한다.
2. fixture·원장·oracle·복제본 검증을 DB 결과와 독립적으로 통과시킨다.
3. N=1,000·32차원·삽입 비율 100%·seed 11, 네 geometry·두 wave 수로 스모크한다.
   평가 질의는 집단당 10개다. 실제 ANN 경로·요청 수·재시작·실패 차단을 확인한다.
4. 평가와 분리한 seed=7에서 튜닝을 완료하고 설정을 동결한다.
5. A → B → C → D 순서로 실행한다. DB·경로 순서를 seed별로 교차 배치한다.
   A의 실제 시간을 이용해 나머지 작업 시간을 산출하고 ledger에 갱신한다.
   예상이 길어져도 조건을 임의로 삭제하거나 seed를 줄이지 않는다.
6. 원시 결과를 재검증하고 집단별 곡선, fresh 대비 gap, 경로 간 gap, 상태 변화,
   자원·시간·실패를 Markdown 보고서와 CSV로 작성한다.

### 반드시 실패해야 하는 검사

- 두 경로의 신규 데이터·최종 데이터 불일치, 중간 인덱스 재생성 또는 clone 불일치.
- 한 번 요청 조건에서 숨은 자동 chunk 분할, 잘못된 wave 경계·벡터 순서.
- 정답 캐시에 이전 D_t를 사용하거나 삽입된 벡터가 DB readback에서 빠지는 경우.
- seqscan 설정 변경·HNSW 제거·다른 인덱스 사용·Qdrant plain fallback.
- telemetry 필드 누락·segment 교체를 성공으로 취급하거나 누락 cell을 완료로 집계.
- 데이터/질의 hash가 다른 fresh 캐시 재사용, 검사 SQL을 지연 타이밍에 섞는 경우.

실제 경계에서 결함을 주입해 탐지되는지 확인한다. 실패 셀은 원시 증거와 최초 오류를
보존한다. 쓰기 결과가 불명확하면 readback으로 확정하기 전 재시도하지 않는다.
읽기 측정 중 segment 교체만 발생한 경우 원본 UNVERIFIED를 남기고 안정화 후
새 attempt ID로 1회만 읽기 재측정을 허용한다. 다시 실패하면 해당 셀은 미완이다.

## 5. 자원·완료 기준·보류 항목

현재 로컬은 M2 24GB, Colima 4 CPU·약 7.7GiB, 호스트 여유 약 37GiB다.
DB별 2 CPU·4GiB를 고정하고 한 번에 한 DB/복제본만 실행한다.
새 이미지 설치 없이 기존 두 ARM64 digest를 재사용한다.

- 추가 공간 목표 1~3GiB, 상한 8GiB, 호스트 여유 하한 25GiB.
- 초기 snapshot 원본과 작업 복제본 하나만 동시에 보유하고 결과 저장·검증 후
  프로젝트 전용 복제본을 정리한다. 기존 Docker 자원과 과거 증거는 보존한다.
- 점수용 입력·정답·벡터는 조건 간 공유하고 거리 행렬은 chunk 계산 후 폐기한다.
  결과는 압축하며 전체 질의 응답·모든 gap의 근거를 보존한다.
- 예상 실행 시간은 1차 파일럿 실측에 근거한 대략 3~5시간이며 확정값이 아니다.
  단계별 4시간의 hard timeout과 정리 watchdog을 별도 프로세스로 구현·주입 검증한다.
  한도 도달 시 미완 cell을 남기며 다음 실행은 완료 원장에서 이어간다.
  한도 초과를 완료로 표시하지 않는다.
- WDL 프로젝트 설정 없이 진행한다는 기존 사용자 선택을 유지한다.

완료는 132개 경로·504개 증분 checkpoint·384개 fresh 측정의 계획/실행 수 일치,
모든 입력·원장·ANN 경로·원시 증거 검증 통과, 실패·미실행 셀 전수 보고로 판정한다.
실패·UNVERIFIED가 남으면 결과 일부를 보고할 수 있으나 전체 완료는 아니다.
품질 하락이나 0.95 미달은 측정 결과이며 이를 이유로 셀을 제거하지 않는다.

최종 보고서는 3개 데이터 seed의 대응 차이와 fresh 구축 반복의 변동을 분리한다.
초기 인덱스를 복제해도 제품의 후속 삽입 PRNG를 같은 seed로 제어할 수 있다는 보장은
없다. 제어 가능 여부를 기록하고, 불가능하면 경로 차이에 신규 노드 구성 난수도
포함됨을 명시한다. 작은 path gap을 배치 분할만의 인과 효과로 단정하지 않는다.
질의 수나 132개 경로를 독립 반복 수로 취급하지 않는다. 3개 seed로 동등성·보편적
우열·제품 내부 위상 결함을 확정하지 않는다. 관찰하지 못한 효과는 검출 한계와 함께 적는다.

실제 임베딩·차원/내재 차원·밀도 독립 변화, 장기 upsert/삭제, 필터·선택도·카디널리티,
Milvus·Weaviate·LanceDB·Vespa 및 클라우드 비교는 전체 연구에서 계속 다룬다.
이번 보고서 검토 시 재개 조건과 비용을 갱신하며, 전체 연구를 완료로 처리하지 않는다.
