# 공개 벡터 실험의 48시간 목표 수정안

작성: 2026-10-26. 상태: **과거 제안, 미적용. 최신 제안은 [12시간 계획](../real-vectors/12h/plan.md)이며 승인 대기.**

아래 실행 상태·시각·전환 절차는 48시간안을 작성한 당시의 기록이다.
이후 기존 실행이 중단됐으며 [실패 조사](../real-vectors/baseline-failure-20261026.md)에 기록했다.

## 사용자 요구와 완료 범위

사용자 요청: “혹시 계획을 2일 안에 끝나게 수정해줄 수 있어?”
현재 로컬 자원에서 증분 갱신과 검색 품질의 관계를 조사한다. 48시간은 새 계획의 실행을
시작한 시각 T0부터 최종 원시 검증과 보고서까지의 벽시계 시간으로 제안한다.
이미 수행한 준비·튜닝·실험을 숨기거나 과거 실행 시간을 초기화하지 않는다.
기존 기본 실험 348개 시나리오와 확장 실험 요구를 삭제하지 않는다.

이 문서의 기본 실험 수는 실제 준비 원장에서 다시 계산했다. 기하·삽입 순서·연속 쓰기·
유지보수·온라인 혼합·재튜닝·필터 확장의 전체 셀 수는 아직 확정되지 않았다.
따라서 **전체 계획을 48시간 내 완수할 수 있다는 검증은 아직 없다.**
기본 실험만 끝내고 전체 완료로 보고하지 않는다. 확장 실험의 미정 조건과 비용이
해소되지 않으면 48시간 전체 완료 인수 기준은 전제 미충족으로 남긴다.

## 실측 근거와 기존 계획의 결함

- MS MARCO/pgvector의 M=64, ef_construction=400, ef_search=256 장기 집중 churn:
  체크포인트 간 평균 약 96.5초. 당시 완료 표본 기준이다.
- 이후 확인한 표본 46개에서 검색·상태검증 point 소요 중앙값 약 39.8초,
  1,000개 삭제·COPY 삽입 wave의 ACK 소요 중앙값 약 57.8초였다.
  ACK에는 클라이언트 인코딩·전송이 포함되며 순수 서버 삽입 시간은 아니다.
- psql은 기존부터 연결과 프로세스를 재사용한다. 질의마다 새 프로세스를 띄우는
  문제라는 앞선 설명은 잘못이었다. 같은 세션에서 계획·검색을 개별 왕복한다.
- 실제 입력 원장: 데이터셋/seed 한 묶음당 fresh 고유 상태 246개,
  DB당 구축 278회. 여섯 묶음·두 DB에서 **3,336회 fresh 구축**이다.
- 이력 4,212개 + fresh 3,336개 = **7,548개 품질 체크포인트**였다.
- 기존 여섯 묶음의 각각 4시간 제한은 완주 비용으로 검증하지 않은 설정이었다.
  현재 첫 묶음 제한은 2026-10-26 20:37:31 KST다. 이 문서는 그 제한을 변경하지 않는다.

## 보존할 조건

- 데이터셋 2종, DB 2종, seed 11/29/47, 원본 768차원·IP.
- N=10,000, 삽입 최대 20,000, 삭제 최소 5,000.
- 29종 × 2 데이터셋 × 2 DB × 3 seed = **348개 시나리오**.
- 1회 갱신 144건, 5회 갱신 144건, 50회 갱신 48건,
  쓰기 없는 50회 대조군 12건. 이력 체크포인트 **4,212개** 유지.
- 초기 physical snapshot 복원, 현재 ID·벡터·버전 exact oracle, 원본 float32 readback.
- PostgreSQL COPY와 동일 ID staging COPY/upsert, seqscan off와 매 질의 HNSW 계획 확인.
  Qdrant의 실제 HNSW 카운터 및 fallback 부재 확인.
- DB 2 CPU/4GiB, 측정 슬롯 1개, 무거운 전처리와 DB 측정 비중첩.
- 호스트 10GiB 하한, 누적 owned output·예약 8GiB 상한, 재생성 불가 증거 보존.
- 실패한 쓰기 자동 재전송 금지. native SUCCESS와 필수 검사 통과 후에만 완료 인정.

## 제안하는 매개변수 변경 — 승인 전 미적용

### 1. 초기·최종 질의 600개, 중간 질의 200개

기존 600개 질의를 고정 모집단으로 보존한다. 초기·최종은 모두 사용한다.
중간은 ANN 결과를 보지 않고 사전에 결정한 동일한 200개 부분집합을 사용한다.
DB와 대응 경로가 같은 부분집합을 사용하고, 현재 상태 exact oracle의 같은 열을 참조한다.

초기·최종 696개 point × 600질의 + 중간 3,516개 point × 200질의
= **1,120,800개 측정 질의**다. 기존 이력 질의 2,527,200개보다 약 55.6% 적다.
중간 곡선의 표본 불확실성은 커진다. 빈 cohort를 다른 집단으로 채우지 않는다.
초기·최종 대비 중간값의 단순 차이는 같은 200개 부분집합에서 재계산해 비교한다.
워밍업도 각 point의 측정 질의 집합과 동일하게 수행한다.

### 2. 재구축 대조군의 시점 조정

모든 시나리오의 최종 상태는 기존처럼 **독립 3회 구축·각 600질의**를 유지한다.
동일한 최종 원장은 기존처럼 중복 제거한다. 50회 경로의 중간 fresh는 10회·25회에
각 1회·600질의를 측정한다. 초기 상태는 read-only 경로의 최종 상태와 원장이 같아
최종 3회 규칙으로 포함된다. 짧은 경로의 중간 fresh와 장기 경로의 나머지 중간 fresh는
이번 제안에서 빠지는 측정이며, 사용자 승인이 없으면 기존 요구로 남는다.

실제 여섯 입력 원장에서 각각:

| 항목 | 기존 | 제안 |
|---|---:|---:|
| fresh 고유 상태 / 데이터셋·seed | 246 | 24 |
| 그중 최종 상태 | 16 | 16 |
| fresh 구축 / DB·데이터셋·seed | 278 | 56 |
| 전체 fresh 구축 | 3,336 | **672** |
| 전체 품질 point | 7,548 | **4,884** |

제안 fresh 질의는 403,200개, 이력 포함 측정 질의 합계는 **1,524,000개**다.
기존 4,528,800개보다 약 66.3% 적다. 워밍업과 계획 확인·진단 질의는 이 합계 외다.
매 갱신의 절대 Recall은 계속 측정하지만, fresh 대비 시점별 격차는 선택된 시점에서만
주장할 수 있다. 측정하지 않은 중간 fresh를 보간해 관측값으로 취급하지 않는다.

### 3. 튜닝 선택에 전체 실행 비용 반영

기존 선택은 Recall 99% 통과 후보 중 검색 최대 p95 최소화였다.
제안은 기존에 측정한 Pareto 후보를 대상으로 **갱신 + 검색 + fresh 구축**의 전체
벽시계 비용을 실제 스모크에서 측정하고, 네 상태의 Recall@10/100 ≥99%를 유지하는
후보 중 48시간 예산에 들어오는 설정을 선택하는 것이다. 가장 작은 M을 자동 선택하지 않는다.

다음 후보는 비용 스모크 대상으로 확인된 값이다. 구축 시간은 네 상태의 합계다.

| 데이터셋 / DB | M, ef_construction, 검색 ef | 최악 Recall@100 | 구축 합계 |
|---|---|---:|---:|
| MS MARCO / pgvector | 16, 100, 1000 | 99.735% | 20.89초 |
| Wikipedia / pgvector | 16, 100, 512 | 99.755% | 22.94초 |
| MS MARCO / Qdrant | 16, 100, 1000 | 99.685% | 12.54초 |
| Wikipedia / Qdrant | 16, 100, 512 | 99.585% | 12.03초 |

현재 pgvector 선택의 구축 합계는 MS MARCO 147.30초, Wikipedia 145.01초다.
낮은 M 후보가 실제 반복 갱신에서도 더 빠를지는 아직 미측정이다.
기존과 다른 설정의 측정값은 별도 캠페인으로 분리한다. 기존 진행 중 데이터와 이어 붙여
한 고정 설정의 완성 이력이라고 부르지 않는다. 비교적 빠른 후보라도 Recall 상한에
가까우면 차이가 가려질 수 있어 Recall 수치와 불확실성을 함께 보고한다.

## 48시간 예산과 입장 조건

아래 시간은 **배정 예산**이다. 검증된 종료 예측이 아니다.

| 단계 | 배정 |
|---|---:|
| 변경 구현·오류 주입 검증·양 DB 비용 스모크 | 4시간 |
| 348개 이력 | 20시간 |
| 672회 fresh | 12시간 |
| 전체 확장 항목의 셀 확정·실행 | 6시간 |
| 원시 검증·대응 분석·보고서 | 2시간 |
| 변동·오류 여유 | 4시간 |
| 합계 | **48시간** |

확장 단계 6시간은 자리 배정이며 실제 실행 가능성의 근거가 아니다. 기존 전체 계획의
I3/I4/I5, 공간 집중 삭제·churn·upsert, 유지보수·회복·온라인 혼합·재튜닝,
선택도·카디널리티·분포·술어·경계 필터를 삭제하거나 완료로 간주하지 않는다.
자연 시간정보 부재와 cardinality 100k > 현 N이라는 기존 전제 미충족도 그대로 남는다.
전체 셀 수·입력 실현 가능성·ANN 증거 경로가 확정되고 비용이 맞아야 그 단계에 입장한다.

비용 스모크는 네 데이터셋/DB 조합에서 복원, 읽기, 쓰기 ACK, 인덱스 구축, native 작업
시작·정리 비용을 분리한다. 초기10k·증가20k·삭제5k·교체10k, 5회 churn/upsert,
50회 경로의 초기와 노후 상태를 포함한다. 이미 다른 설정으로 실행한 노후 표본을
새 설정의 표본으로 대신하지 않는다. 단계별 p90 관측 비용과 남은 실제 작업 수로
예측표를 만들고, 전체 합이 **44시간 이하**여야 4시간 여유를 남기고 본 실행에 진입한다.

비용이 맞지 않으면 질의·시나리오·seed·확장 항목을 자동으로 더 줄이지 않는다.
해당 수치와 어떤 기준이 충돌하는지를 보고하고 미완료로 남긴다.

## 실행 전환과 재개

1. 현재 실행은 동결된 코드와 기존 제한을 유지한다. 계획 작성만으로 중단·연장하지 않는다.
2. 매개변수 승인과 전환 구현 후 현재 worker를 안전한 경계에서 마무리하고,
   기존 드라이버가 다음 미검증 작업을 시작하지 않도록 소유 프로세스 전환 절차를 둔다.
   첫 이력을 완주하면 보존한다. 설정이 바뀌면 새 캠페인에서 해당 이력도 새로 수행한다.
3. 원래 setup/실험의 manifest·receipt·deadline은 수정하지 않는다. 검증된 source·원장·oracle와
   튜닝 원시 증거만 호환성을 확인해 재사용한다. 과거 성공을 새 실험의 성공으로 대체하지 않는다.
4. 새 캠페인은 T0와 T0+48h의 단일 전역 기한을 manifest에 고정한다. controller, driver,
   worker, watchdog, guardian 모두 같은 남은 기한을 소비하고 재개 시 초기화하지 않는다.
   현재 드라이버의 14,460초 대기 제한만 바꾸는 것으로 해결했다고 하지 않는다.
5. DB 1개 제한과 Dagster 의존성을 유지한다. 초기 각 DB 비용 스모크와 짧은 시나리오를
   우선 배치하여 한 장기 시나리오가 끝나기 전에도 양 DB의 실행 비용을 확보한다.
6. 완료된 native 시나리오를 receipt·source·입력·설정 해시로 검증해 건너뛰며,
   미완료 쓰기는 상태 확인 없이 이어 쓰거나 재전송하지 않는다. 통째로 새 이력을 시작할 때도
   실패 증거를 보존하고 추가 비용을 남은 전역 예산에 반영한다.

## 인수 기준과 반증

- [ ] 사용자에게 중간 질의 수·중간 fresh 축소·튜닝 선택 변경을 승인받고 기록한다.
- [ ] 새 부분집합의 query/oracle/cohort 매핑을 검증한다. 다른 열·현재 상태 아닌 oracle을
  일부러 넣으면 차단돼야 한다.
- [ ] 원래 계획 348개/4,212개, 새 fresh 672개를 실행표에서 실제로 세고 누락을 거부한다.
- [ ] 양 DB 비용 스모크와 노후 상태 측정이 성공하고 남은 전체 비용 p90 추정 ≤44시간이다.
- [ ] 초기·최종 600개, 중간 200개, fresh 600개 질의 수를 raw 결과로 검증한다.
- [ ] 매 질의 seqscan off·HNSW 계획 / Qdrant ANN 증거 경로가 동작한다.
  fallback을 의도적으로 유도하면 완료 보고가 차단돼야 한다.
- [ ] 전역 만료·부모 종료·실패 후 정리 경로를 짧은 fixture로 실제 실행한다.
  재개나 새 shard 생성으로 T0+48h를 늘리려 하면 거부돼야 한다.
- [ ] 기존 전체 확장 요구를 행별로 매핑하고 셀 수·선행 조건·실행 증거가 모두 충족된다.
  누락·전제 미충족·미실행이 하나라도 있으면 전체 완료를 선언하지 않는다.
- [ ] 최종 원시 증거·fresh 3회 범위·질의별 대응 불확실성·환경 제한을 보고한다.

현재 이 문서의 구현/실험 검증 체크박스는 모두 미충족이다.
