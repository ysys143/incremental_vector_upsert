# 공개 벡터 기반 증분 갱신 연구 계획

작성: 2026-10-25. 상태: 구현 중, 실제 데이터 스모크·본실험 NOT RUN.
2026-10-26 사용자 `proceed anyway` 재개 지시로 `realstudy`의 호스트 여유 하한을
25GiB에서 10GiB로 변경했다. 추가 사용량 상한 8GiB, DB 1개 및 CPU/IO 준비 2개 제한은
유지한다. 이전 수집 창이 만료되어 새 실행을 시작했고, 이전 실패와 시간 기록은 보존한다.
아래 25GiB 수치는 최초 계획의 이력이며 현재 실제 입장 조건은 10GiB다.
이 문서는 대화에서 합의한 범위를 보존한다. 완료 수는 새 캠페인의 원장과 native
Dagster run·검사·원시 증거로 판정한다. 과거 합성 결과는 실제 데이터 결과가 아니다.

## 목표와 선행 연구

실제 임베딩의 삽입·삭제·동일 ID 교체에서 검색 품질이 어떻게 변하는지,
현재 데이터의 검색 난도와 갱신 이력의 차이를 분리한다. 기존 합성 실험의 132개
삽입 경로에 대응하는 조건을 재실험하고 새로운 삭제·교체 경로를 추가한다.
최종 경로 수는 확정된 실험표로 다시 센다. 132개나 888개를 새 전체 수로 전용하지 않는다.

관련 자료와 제품 비교의 한계는 `insertion-study-literature-audit.md` 및
`insertion-study-product-benchmarks.md`를 따른다. 공개 벤치마크의 적재율 보정 Recall을
현재 생존 집합의 Recall로 사용하지 않는다.

## 데이터와 로컬 규모

| 항목 | 기준 |
|---|---|
| 공개 벡터 | MS MARCO Web Search–SimANS, Wikipedia–Cohere |
| 형식 | 원본 768차원 float32, 새 임베딩 생성·인위적 벡터 이동·차원 축소 없음 |
| 검색 기준 | Big ANN 원본 정의의 최대 내적(IP); DB와 oracle 모두 같은 기준 |
| 원본 풀 | 데이터셋별 100,000개; 추출 위치와 원본 row ID를 기록 |
| 초기 크기 | 10,000개; 삽입 최대 20,000개; 삭제 최종 최소 5,000개 |
| 반복 | 평가 seed 11·29·47, 별도 튜닝 seed 7 |
| 질의 | 튜닝 200개, 평가 600개; 중복·문서/질의 분리 확인 |
| 짧은 갱신 | 초기 크기의 10%씩 5회 |
| 긴 갱신 | 삭제+삽입·동일 ID 교체를 초기 크기의 10%씩 50회 |

MS MARCO의 검색 질의와 Wikipedia의 문서 유래 질의를 구분해서 보고한다.
정규화·거리 함수·파일 헤더·배포 주소·ETag·해시를 고정한다. 제공된 정답은 파일 검증의
보조 자료이며, 변경 후 정답은 실제 ID·최신 벡터 값과 질의로 다시 계산한다.
외부 모델의 벡터끼리 섞지 않는다. 실제 벡터를 재배치한 upsert는 실제 문서 수정 이력의
재생이라고 표기하지 않는다.

공간 조건은 자연 데이터의 군집·이웃 구조와 거리/유사도 실현값으로 정의한다.
같은 모집단·인접·분리·연결 영역을 선택하고 실제 교차 이웃 비율·밀도·연결성을
보고한다. 희망하는 구조가 실제로 없으면 벡터를 변형하지 않고 입력 조건 미충족으로 남긴다.
서로 다른 반복 사이의 원본 row 중복을 보고하며 세 seed를 세 독립 코퍼스로 부르지 않는다.

공식 데이터 로더: https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/benchmark/datasets.py

짧은 churn/upsert는 한 번에 5,000개 변경과 1,000개씩 5회 변경을 비교한다.
동일 총량 대응 경로에서는 대상 ID와 교체 벡터를 고정하며 동일 ID가 한 SQL batch에
중복되지 않도록 한다. 같은 ID의 반복 갱신은 별도 이력이다. 이때 최종 버전만 한 번에
쓰는 대조군은 총 쓰기량이 다르므로 순수한 batch 비교로 부르지 않는다.

필터 축: 통과 비율 100·10·1·0.1·0.01%, 카디널리티 10·1천·10만, 균등/편향,
이웃과 독립/집중/엇갈림, 단일/복합/범위, 벡터/메타데이터 갱신, 후보 0/<k/≥k.
카디널리티 10만은 현재 최대 생존 집합 2만에서는 성립하지 않으며 규모 확장 항목으로
유지한다. 원본 메타데이터와 실험용 라벨을 구분한다. 원본에 없는 시간을 자연적인
시간순이라고 부르지 않는다. 데이터·자원 미충족 항목을 완료 수에서 빼서 성공으로 만들지 않는다.

## 대조군·지표·튜닝

같은 초기 인덱스의 정상 종료 snapshot에서 대응 경로를 분기한다. 각 checkpoint는
현재 ID와 최신 벡터를 전체 readback으로 확인하고 현재 상태의 exact top-100과 비교한다.
같은 상태·질의·동결 설정의 fresh 인덱스를 별도 구축한다. 최종 fresh는 3회 구축하고
중간 fresh는 1회로 두어 구축 편차와 데이터 seed 편차를 구분한다.

Recall@10·100, 결과 부족·삭제 ID·구버전/중복 반환, 기존/신규/갱신/경계 질의 점수,
fresh 차이, 대응 경로 차이, p50/p95/p99·처리량·오류, 쓰기 확인·가시성·인덱싱 대기,
CPU·RAM·I/O·디스크·정리 비용을 보고한다. 0개 후보는 빈 결과 정확성과 Recall N/A로
분리한다. 온라인 질의의 현재 상태를 확정할 수 없으면 단일 Recall을 부여하지 않는다.

실제 입력에서 DB별로 다시 튜닝한다. 합성 실험의 승자 설정을 그대로 승계하지 않는다.
튜닝과 평가 입력을 분리하고 공개 탐색 범위·자원 예산에서 최선의 구성을 선택한다.
기본 갱신 품질 곡선에서는 설정을 동결하고, 재튜닝 회복 실험은 별도 결과로 낸다.
품질 목표 0.95·0.99별 Pareto 비교를 유지하며 세 seed로 동등성이나 보편적 순위를 주장하지 않는다.

PostgreSQL은 초기 COPY 후 인덱스 구축, 증분 COPY, 동일 ID에는 staging COPY 후
upsert를 구현한다. 각 wave는 별도 트랜잭션이다. 갱신 중 전체 REINDEX는 하지 않는다.
Qdrant는 같은 collection의 batch API·정상 optimizer를 사용한다. 최대 단일 payload를
스모크에서 확인하고 수신 한도를 명시한다. 숨은 chunk 분할은 실패다.
PostgreSQL의 seqscan off와 실제 지정 HNSW 실행, Qdrant의 실제 HNSW 및 plain/exact
fallback 배제를 검증한다. 필터 검색의 증거는 현재 unfiltered 전용 검사와 별도로 검증한다.

## 자원·DAG와 병렬화

- Docker VM 제공 자원 4 CPU·약 7.7GiB, DB별 2 CPU·4GiB, DB 측정 슬롯 전체 1개.
- 다운로드 최대 2개, CPU 전처리/분석 최대 2개. 내부 BLAS thread 수도 고정한다.
- DB 측정 중에는 무거운 다운로드·압축·oracle·분석을 겹치지 않는다.
- 같은 이력의 wave는 순차이며 독립 경로·fresh는 자원 슬롯이 허용할 때만 실행한다.
- 추가 공간 목표 4~6GiB·상한 8GiB, 호스트 여유 하한 25GiB. 기존 증거는 보존한다.
- 측정 전 이 실험 소유가 아닌 실행 컨테이너와 공간·메모리 상태를 점검한다.
  사용자는 '경합 없는 구간에 측정'을 선택했다. 타 작업은 자동 중단/삭제하지 않는다.
- 단계별 원래 4시간 상한은 재개로 연장하지 않는다. 전체 시간은 실제 데이터 스모크로 산출한다.

공개 source → 검증 → 표본/원장 → oracle/기하 → 스모크 → 튜닝 → 초기 snapshot →
증분/fresh → 원시 검증 → 대응 분석 → 보고서를 Dagster asset 의존성으로 연결한다.
런 큐·동시성은 엔진이 관리한다. 공통 JSON read-modify-write 원장을 없애고, native run
상태와 셀별 해시 receipt를 정본으로 삼는다. 조회용 원장은 이들로부터 생성한다.
같은 셀 중복 실행·다른 캠페인의 성공 차용·잘못된 소스/입력 재사용을 거부한다.
완료 셀은 재실행하지 않는다. 실패한 쓰기는 자동 재전송하지 않는다. native 성공만이 아니라
필수 검사 통과를 보고서 생성의 blocking 선행 조건으로 둔다.
별도 watchdog이 시간 초과·부모 사망·실패 후 전용 자원을 정리한다. 로그와 첫 오류는 보존한다.
Dagster 관리 프로세스는 캠페인 기간에만 실행한다. 상시 스케줄·유료 API·클라우드는 사용하지 않는다.
에이전트는 설계·예외 판단·결과 해석을 담당하고 진행 상태를 상시 폴링하지 않는다.

## 스모크·인수 조건

실제 768차원 벡터 1,000개 스모크 후 10,000개 최대 요청과 장기 이력을 검증한다.
정답·원장·clone·삭제·upsert·실제 ANN·재시작·정리 경로를 확인한 뒤 본실험에 진입한다.
CPU 두 작업 병행/세 번째 대기, DB 동시 활성 1개, DB와 무거운 준비의 비중첩,
병렬 receipt 충돌 없음, 동일 셀 동시 실행 거부, 완료 ack 불변, 실제 데이터 provenance
오류 거부, 필수 검사 실패 후 보고서 차단, 시간 초과·부모 사망 후 독립 정리를 주입 검증한다.

## 현재 실행 전제와 미완 항목

2026-10-25 재개 점검에서 Codex 셸의 일반 DNS 조회는 실패했다. 별도 Docker 네트워크의
동일 공식 호스트 이름 해석과 curl의 명시적 주소 연결에서는 MS MARCO 질의 파일의
HEAD 및 16-byte Range가 성공했다(헤더 9,376×768). OS DNS·권한은 변경하지 않았다.
이 경로는 실제 데이터 전체 확보나 스모크 성공이 아니다.

같은 시점 호스트 여유가 약 22.6GiB로 25GiB 하한보다 낮았다. 데이터 적재·DB 실행은
차단하며 작은 문서·코드·단위 검증만 진행한다. 공간 회복·데이터 확보 후 예산을 재검증한다.
전체 교차 조합표·정확한 셀 수·자연 메타데이터/시간 정보·입력 집단 선정 문턱·튜닝 탐색
예산·온라인 부하 수준은 코드 실행표에서 명시해야 한다. 미정이면 본실험 진입을 거부한다.

Milvus·Weaviate·pgvector IVFFlat, 더 큰 규모·클라우드 비교는 보관된 전체 연구의 미실행
범위로 유지한다. 로컬 2 DB 결과로 전체 연구 완료를 선언하지 않는다.
