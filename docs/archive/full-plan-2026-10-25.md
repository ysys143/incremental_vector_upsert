# 벡터DB 증분 삽입·삭제의 검색 품질 및 성능 비교 계획

## 1. 목적과 비교 원칙

동일한 데이터에 삽입·삭제·갱신을 반복할 때 각 DB의 검색 품질이 어떻게 변하고, 이를 유지하기 위해 얼마나 많은 시간·자원·유지보수 비용이 필요한지 측정한다.

“최선의 튜닝”은 절대적 최적값을 주장하는 대신, **공개한 탐색 범위와 자원 예산 안에서 검증한 최선의 설정**으로 정의한다. 공정성은 동일한 파라미터가 아니라 동일한 데이터·자원·내구성 조건과 품질 목표로 확보한다.

기본 비교 대상은 PostgreSQL+pgvector, Qdrant, Milvus, Weaviate다. pgvector는 HNSW와 IVFFlat을 별도 구성으로 취급한다. 다른 DB도 이론 검토에서 증분 갱신에 적합한 공식 지원 인덱스가 확인되면 별도 실험 구성으로 등록한다. DB 간 결과와 동일 DB 내 인덱스 비교를 구분한다.

주요 산출물은 다음과 같다.

- 이론 검토 및 출처를 담은 Markdown 보고서.
- DB별 최적화 근거와 스모크 통과 증거.
- 클라우드에서 재현 가능한 실험 하네스·설정·실행 명령.
- 원시 결과, 실패 기록, 통계 분석, 품질·성능·비용 비교 보고서.

## 2. 실험 전에 검토할 이론적 쟁점

이론 검토를 선행 단계로 두고, 각 항목을 **가설 → 교란 요인 → 실험 → 판정 지표**로 연결한다.

| 쟁점 | 검토 내용과 실험상 대응 |
|---|---|
| 인덱스의 이력 의존성 | 최종 데이터가 같아도 삽입 순서·삭제 이력에 따라 그래프가 달라지는지 확인. 같은 최종 데이터로 새로 구축한 인덱스를 대조군으로 사용 |
| 삭제와 연결성 | 논리 삭제, 물리 삭제, 그래프 복구, 슬롯 재사용을 구분. 무작위 삭제와 특정 군집 집중 삭제 비교 |
| 데이터 분포 변화 | 같은 분포의 신규 데이터와 새로운 군집 유입을 구분. IVF 계열의 중심점 노후화·재학습 필요성 검토 |
| 검색 오차와 반영 지연 | 근사 검색 실패와 아직 검색에 보이지 않는 데이터를 구분. 쓰기 확인 시간과 검색 가시성 지연을 각각 측정 |
| 유지보수와 회복 | VACUUM·compaction·merge·그래프 정리가 품질을 회복하는지, 검색 지연과 쓰기 처리량에 어떤 비용을 주는지 측정 |
| 품질의 의미 | 정확한 최근접 이웃 대비 재현율과 사용자 관련성 품질을 구분. 관련성 라벨이 있는 데이터에서는 NDCG·MRR도 별도 평가 |
| 필터와 실행 경로 | 사전·사후 필터, 탐색 중 필터, 전수 검색 전환, 파티셔닝의 영향을 구분 |
| 공정한 최적화 | 고정 설정의 노후화와 재튜닝 후 달성 가능한 성능을 모두 측정. 재튜닝으로 열화를 숨기거나 고정 설정으로 특정 DB를 불리하게 만들지 않음 |

출발 자료는 FreshDiskANN, IP-DiskANN, HNSW 업데이트 연구와 각 DB의 공식 문서·소스다. 논문의 알고리즘 결과를 제품 전체의 성능으로 일반화하지 않는다.

참조 저장소는 `just-dag-it`의 반복 실험 관리와 `pg-extension-lab`의 동일 품질 비교·실행 경로 증명 원칙을 활용한다. 기존 예제 하네스의 정적 데이터와 작은 스모크 결과는 이번 동적 실험의 증거로 사용하지 않는다.

공유 ChatGPT 대화는 `ego-browser` 시작 실패로 아직 확인하지 못했다. **참조 대화 검토가 끝나기 전까지 요구사항 동결은 미완**으로 표시하고, 접근 문제 해결 후 본 계획과 차이를 반영한다.

## 3. 실험 설계와 튜닝

### 데이터와 업데이트 시나리오

실제 임베딩 데이터 두 종류와 통제 가능한 합성 데이터를 사용한다. 실제 데이터는 텍스트 검색용 고차원 데이터와 다른 차원·분포의 공개 ANN 데이터를 선정한다. 이론 검토 단계에서 라이선스·버전·다운로드 위치·해시를 고정한다. 합성 데이터는 군집 구조와 필터 상관관계를 조절하는 용도다.

모든 DB는 같은 벡터, 거리 함수, ID, 질의, 변경 이벤트를 사용한다. 정규화와 정밀도를 고정하며, 압축·양자화는 원본 정밀도 실험 뒤 별도 조건으로 비교한다.

기본 시나리오는 다음 여섯 가지다.

1. **삽입만:** 초기 데이터 대비 10%, 25%, 50%, 100% 증가.
2. **삭제만:** 초기 데이터의 10%, 25%, 50% 삭제.
3. **일정 크기 churn:** 매 회차 10% 삭제·동량 삽입을 20회 반복.
4. **동일 ID 갱신:** 벡터 교체와 메타데이터만 변경하는 경우 분리.
5. **편향된 변경:** 특정 군집과 자주 갱신되는 ID에 변경 집중.
6. **분포 이동:** 새로운 군집 유입 및 기존 군집의 단계적 퇴출.

매 시나리오는 독립된 초기 상태에서 시작한다. 이벤트 순서는 seed로 고정하고 DB 간 공유한다. 갱신은 ID·버전 기준으로 검증하며, 삭제 후 같은 ID 재삽입도 정확성 시험에 포함한다.

### 세 가지 측정 상태

- **안정 상태:** 정해진 변경 배치가 검색에 반영된 뒤 품질 측정.
- **온라인 상태:** 검색과 변경을 동시에 수행하며 지연·처리량·가시성 측정.
- **회복 상태:** 쓰기를 멈춘 뒤 정상 유지보수에 따른 회복 시간과 잔여 열화 측정.

별도의 재구축 대조군은 동일한 최종 생존 데이터로 새 인덱스를 만든다. 같은 설정에서 비교해 이력 효과를 측정하고, 재튜닝한 재구축 결과는 별도로 보고한다.

### 튜닝 기준

재현율 목표는 Recall@10 및 Recall@100의 0.95·0.99로 설정한다. 목표를 충족하는 설정들의 검색 지연·처리량·업데이트 처리량·자원 사용량을 Pareto 곡선으로 비교한다. 목표 미달 구성은 탈락 사실과 최선의 도달값을 보고한다.

각 DB에 동일한 튜닝 자원 시간 상한을 적용한다. 공식 권장 구성에서 시작해 적재 방식, 인덱스 구축, 검색 탐색량, 유지보수, 동시성을 단계적으로 조정한다. 전체 탐색 내역과 예산 소진 여부를 보존한다.

튜닝용 질의·변경 이력과 평가용 질의·변경 이력을 분리한다. 본시험에서는 다음 두 결과를 함께 낸다.

- 초기 최적화 설정을 고정했을 때의 품질·성능 변화.
- 사전 정의한 절차로 재튜닝했을 때의 회복 수준과 비용.

### PostgreSQL을 포함한 DB별 적재 최적화

스모크에서 실제로 다음 경로를 실행하고 병목을 확인한다.

| 작업 | PostgreSQL 검증 경로 |
|---|---|
| 초기 적재 | `COPY FROM STDIN` 후 인덱스 구축·`ANALYZE`. 전체 검색 준비 시간 포함 |
| 증분 삽입 | 기존 인덱스를 유지한 `COPY`, 배치 크기·동시성 비교 |
| 기존 ID 갱신 | 배치 upsert와 스테이징 `COPY` 후 병합 비교. 전송·스테이징·병합·커밋 비용 포함 |
| 삭제 | 집합 기반 삭제와 배치 조절, VACUUM·인덱스 정리 관찰 |
| 검색 | 실제 실행 계획, 인덱스 사용, iterative scan 및 전수 검색 전환 확인 |

초기 적재와 온라인 갱신은 다른 작업으로 측정한다. 초기 적재의 인덱스 후생성 최적화를 온라인 삽입 성능으로 계산하지 않는다. PostgreSQL의 `COPY` 및 인덱스 후생성 권고는 [공식 대량 적재 문서](https://www.postgresql.org/docs/current/populate.html)를 기준으로 확인한다.

다른 DB도 공식 bulk·batch 경로, 전송 프로토콜, 연결 재사용, 병렬성, 인덱스 구축 시점과 정리 정책을 동일하게 검토한다. 클라이언트 직렬화·CPU·네트워크 병목을 계측한다. 내구성이나 가시성 보장을 낮춘 설정은 별도 조건으로 표시한다.

## 4. 클라우드 실행 단계와 통과 기준

### 공정한 실행 환경

동일 공급자·리전·인스턴스 유형·CPU 아키텍처·스토리지 성능의 독립 인스턴스를 사용한다. 하나의 DB 실험이 다른 DB와 CPU·메모리·스토리지를 공유하지 않도록 한다. Milvus 등의 필수 의존 서비스도 해당 구성의 자원·비용에 포함한다.

부하 발생기는 DB와 분리하고 동일 네트워크 배치로 운영한다. exact oracle 계산과 재구축 대조군 작업은 측정 대상 자원을 잠식하지 않도록 별도 실행한다.

버전·이미지 digest·설정·CPU 모델·디스크 성능·커널을 기록한다. 실행 순서는 반복별로 바꾸며 warm-cache와 cold-start 결과를 구분한다. 독립 VM만으로 물리 호스트 간섭이 완전히 제거되었다고 주장하지 않고, 자원 편차와 노이즈를 기록한다.

### 단계별 실행

| 단계 | 규모와 목적 | 다음 단계 진입 기준 |
|---|---|---|
| 방법론 검증 | 작은 결정적 데이터 | exact oracle, ID·버전·삭제 의미, 결과 집계 검증 |
| 기능 스모크 | 1만 벡터, DB별 전체 경로 | 적재·삽입·삭제·갱신·검색·재시작 검증 |
| 최적화 스모크 | 10만 벡터부터 확대 | 실제 ANN·정리 경로 확인, 적재 병목 해소, 튜닝 근거 확보 |
| 본시험 | 100만 벡터, 독립 반복 5회 | 기본 시나리오 전체와 재구축 대조군 확보 |
| 규모 확장 | 1천만 벡터 및 메모리 초과 조건 | 데이터 규모·메모리 압력 효과 평가 |
| 필터 확장 | 기본 시험 이후 | 선택도·카디널리티·상관관계·변경의 상호작용 평가 |

작은 데이터에서 전수 검색만 수행되거나 유지보수가 발생하지 않으면 스모크를 통과시키지 않는다. 관찰에 필요한 크기까지 확대하고 변경 이유를 기록한다. 10만 벡터에서 얻은 설정을 100만·1천만의 최적값으로 가정하지 않고 각 규모에서 재검증한다.

필터 확장은 다음 축을 포함한다.

- 통과 비율: 100%, 10%, 1%, 0.1%, 0.01%.
- 필드의 고유값 수: 10, 1천, 10만.
- 균등 분포와 편향 분포.
- 벡터 이웃과 필터 조건의 독립·양의 상관·반대 상관.
- 단일 조건, 복합 조건, 범위 조건, 메타데이터 갱신.
- 필터 통과 후보 수가 0, k 미만, k 이상인 경계 사례.

선택도는 필터를 **통과하는 비율**로 정의한다. 필드 카디널리티와 실제 통과 후보 수를 별도로 기록한다. 전체 조합의 무차별 실행 대신 모든 축을 포함하는 사전 등록 실험표와 핵심 상호작용 조합을 사용한다.

## 5. 검증·자동화·보고 및 실행 전제

### 품질과 통계

변경 이벤트 원장을 정본으로 삼아 각 checkpoint의 생존 ID·최신 벡터를 확정하고, 그 데이터에 대해 exact top-k를 계산한다. 필터 시험은 필터 통과 집합 내부에서 정답을 계산한다. 동점 처리 규칙을 고정하고, oracle은 독립 구현과 작은 수작업 사례로 교차 검증한다.

온라인 쓰기 중에는 질의의 정확한 데이터 시점을 확정할 수 없는 결과에 단일 Recall 값을 부여하지 않는다. 확정된 checkpoint의 품질과 동시 부하 상태의 지연·처리량·가시성 지연을 구분한다.

측정 지표는 다음을 포함한다.

- Recall@10·100, 결과 부족률, 삭제 ID·이전 버전 반환률.
- 신규·갱신 데이터와 기존 데이터의 재현율.
- 검색 p50·p95·p99, 처리량, timeout·오류율.
- 쓰기 확인 지연, 검색 가시성 지연, 지속 가능한 변경 처리량.
- CPU·메모리·디스크·I/O·네트워크, 저장 공간 증가, 유지보수 비용.
- 같은 최종 데이터의 재구축 인덱스 대비 품질·성능 차이.

부하는 고정 도착률과 포화 탐색을 구분하고, 클라이언트 대기 시간 및 미완료 요청도 기록한다. 5회의 독립 반복을 통계 단위로 삼아 신뢰구간을 보고한다. 반복 횟수와 실패 실행을 숨기지 않으며 질의 개수를 독립 실험 횟수처럼 취급하지 않는다.

### 하네스와 DAG

하네스는 데이터·변경 시나리오·DB 어댑터·측정·보고를 분리한다. 어댑터에는 초기 적재, 삽입, 갱신, 삭제, 검색, 가시성 확인, 상태 수집, 재구축 기능을 둔다. 지원되지 않는 기능을 조용히 모사하지 않고 명시한다.

Dagster는 검증된 반복 실행을 담당한다. 각 실행은 데이터 해시·이벤트 seed·DB 버전·설정·규모·반복 번호로 식별한다. 완료 결과는 보존하고 실패·중단·미실행을 구분한다. 측정 중 부분 적용된 쓰기는 무조건 재시도하지 않으며, 새 실행 ID와 초기 상태로 재현한다.

의도적으로 오래된 정답, 누락된 변경, 잘못된 버전 반환, 전수 검색 위장, 실패 결과 누락을 주입해 검증기가 실제로 실패하는지 확인한다. 시간 제한·비용 상한·실패 후 자원 해제도 실제 실행 경로에서 검증한다.

### 전제와 완료 기준

현재는 계획 단계다. 클라우드 공급자·실제 가격·총예산이 확정되지 않았으므로 인스턴스 생성은 시작하지 않는다. 실행 견적에는 튜닝·oracle·재구축·재실행·스토리지 비용까지 포함하며, 예산이 부족해도 범위를 임의로 줄이지 않는다.

기본값은 자체 호스팅·단일 노드·복제본 1개·동일 자원 비교다. 분산 고가용성이나 관리형 서비스의 제품 비교로 확대할 경우 별도 조건을 추가한다.

완료는 기본 시나리오 6종, 규모 확장, 필터 확장, DB별 튜닝 근거, 원시 증거, 재현 명령이 모두 갖춰졌을 때 판정한다. 실패하거나 자원 한계로 수행하지 못한 항목은 원인과 재개 조건을 기록하고 전체 완료와 구분한다. 최종 보고서는 어떤 조건에서 품질이 유지·저하·회복되는지와 그 비용을 제시하며, 결과가 뒷받침하지 않는 단일 종합 순위는 만들지 않는다.

## 보존 부록: 후속 논의와 추정의 한계

- 전체 비용 $2,500~$7,500은 실행 시간을 측정하지 않은 초기 추정이며 확정 견적이 아니다.
- 단일 클라우드 인스턴스에서 DB를 순차 실행하는 방안이 논의되었다. 임대 시간과
  node-hours가 같으면 인스턴스 수 감소만으로 계산 비용이 비례 감소하지 않는다.
- 로컬 M2 24GB, Colima 4 vCPU/약 7.7GiB, 디스크 여유 약 42GiB를 확인했다.
- 사용자가 최소 로컬 파일럿을 먼저 요청했다. 전체 연구는 보류이며 철회·완료가 아니다.
- 로컬 파일럿은 두 DB·작은 합성 데이터·배치 증분의 측정 가능성 검증이다.
- 공유 대화는 ego-browser 시작 실패로 미확인. 원문 접근 성공이나 요구사항 동결을 주장하지 않는다.
