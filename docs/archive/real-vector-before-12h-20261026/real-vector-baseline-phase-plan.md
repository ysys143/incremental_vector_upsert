# 공개 벡터 기본 실험 실행표

> 2026-10-26: [48시간 목표 수정안](real-vector-48h-plan.md)을 작성했다.
> 매개변수 승인 전 제안이며 현재 실행 조건은 이 문서의 기존 값이다.

이 단계는 전체 연구의 기본 조건이다. 기하·삽입 순서·연속 쓰기·유지보수/회복·온라인 혼합·
재튜닝·필터 단계는 전체 계획에 그대로 남으며, 이 단계 완료를 전체 완료로 부르지 않는다.
사용자의 `proceed anyway` 지시에 따라 여유 하한은 10GiB, 추가 사용량 상한은 기존 8GiB다.
이미 사용한 공간을 제외하고 새 상한을 시작하지 않는다.

## 고정 조건

- 데이터: 검증된 MS MARCO–SimANS와 Wikipedia–Cohere, 원본 768차원 float32·IP.
- DB: PostgreSQL+pgvector HNSW, Qdrant HNSW. DB별 2 CPU·4GiB, 전역 측정 슬롯 1개.
- 초기 N=10,000, 삽입 최종 최대 20,000, 삭제 최종 최소 5,000.
- 평가 seed 11·29·47, seed마다 평가 질의 600개. 세 seed를 세 독립 코퍼스로 취급하지 않는다.
- calibration 질의 200개와 문서 20,000개를 전 평가 seed의 입력에서 제외한다.
- 현재 공개 풀 100,000개에서 초기와 50회 변경에 필요한 새로운 50,000개 source row를 확보한다.
  동일 벡터 제어군 외에 변경 벡터의 source row를 해당 이력 안에서 재사용하지 않는다.
- 검색 대상은 매 checkpoint의 현재 ID·벡터·버전 원장이다. 허용 오차 없이 원본 float32 값을
  실제 readback과 대조한다. PostgreSQL seqscan off·실제 HNSW 계획, Qdrant HNSW 카운터와
  fallback 부재를 계속 검증한다.

## 경로와 측정 수

다음 수는 데이터셋 × DB × seed 한 조합당이며, 전체 조합은 2×2×3=12개다.

| 조건 | 경로 수 | 이력 checkpoint 수 |
|---|---:|---:|
| 삽입 10/25/50/100%, 한 번/5회 | 8 | 32 |
| 삭제 10/25/50%, 한 번/5회 | 6 | 24 |
| churn/upsert/동일 벡터 새 ID/동일 ID 같은 벡터/메타데이터, 50% 한 번/10%씩 5회 | 10 | 40 |
| churn/upsert, 무작위/반복 집중 대상, 10%씩 50회 | 4 | 204 |
| 쓰기 없는 반복 검색 50회 | 1 | 51 |
| 합계 | 29 | 351 |

전체 이력은 **348개**, 이력 품질 측정은 **4,212개**다. fresh는 동일한 원장·질의·설정의
상태를 중복 제거한 뒤 최종 상태당 3회, 중간 상태당 1회 구축한다. 이 수는 native 입력 준비
결과로 확정한다. 이전 합성 실험의 888개 측정 수를 전용하지 않는다.

## 설정 선택과 질의 집단

calibration은 initial 10,000·growth 20,000·delete 5,000·replacement 10,000의 별도
문서 집합에서 수행한다. build 후보는 (m,ef_construction)=(16,100)/(32,200)/(48,300)/(64,400),
검색 ef는 100/128/256/512/1000, 초기 batch는 100/1,000/10,000이다.
네 상태 모두에서 Recall@10/100 목표 0.95/0.99를 만족하는 후보의 지연·구축 비용 Pareto를
기록한다. 기본 이력은 0.99 조건에서 최대 p95가 가장 작은 설정을 선택하고 세 평가 seed에
동일하게 고정한다. calibration 통과가 모든 평가 checkpoint의 0.99를 보장하지는 않는다.

초기 setup의 큰 HNSW 후보가 검색용 120초 statement timeout에 걸렸다. 재개 setup은 입력
2개·준비 barrier·load probe 4개·구축/상태 그룹 64개·설정 선택 4개·보고서의 76개 native
노드로 나눈다. 실패한 calibration의 부분 값은 선택에 사용하지 않고, 성공한 입력만 native
증거를 검증해 재사용한다. DDL은 600초, 검색은 120초로 제한한다. 600초 구축 제한에 걸린
후보는 품질값을 만들지 않고 예산 내 실행 불가로 기록한다.
PostgreSQL은 테이블 parallel_workers=1과 max_parallel_maintenance_workers=1을 설정해
leader와 worker가 2 CPU 한도 안에서 구축하도록 요청한다. Docker 공유 메모리 한도는 1GiB,
컨테이너 전체 메모리는 기존 4GiB다. 검색의 실제 HNSW 계획 검증은 그대로 유지한다.

Docker stats의 실제 출력에 ANSI 제어문자가 포함돼 첫 sampler가 비었다. 출력 파서를
수정하고 별도 실제 Docker helper로 표본 수집·종료를 검증했다. 표본의 실제 시간은 각
JSONL의 time 필드가 기준이며 현재 CLI 갱신 간격은 대략 0.5~1초다.

질의는 ANN 결과와 무관하게 미리 고정한다. exact top-10의 변경 이웃 비율이 80% 이상이면
변경 집단, 20% 이하이면 유지 집단, 그 사이는 boundary로 표시한다. 삭제는 초기 정답에서
삭제된 이웃의 비율을 사용한다. 메타데이터·재삽입 집단은 새 임베딩이라고 부르지 않는다.
집단별 실제 질의 수를 보고하며 빈 집단을 만들어 채우지 않는다.

## 실행·해석 경계

native 입력 준비(CPU 최대 2개) → 공통 calibration(DB 슬롯 1개) → 데이터셋/seed별 실행
조각 6개를 순서대로 연결한다. 조각마다 초기 physical snapshot을 동일 DB의 경로에 복원한다.
각 실행 조각의 4시간 상한은 재개로 초기화하지 않는다. 무거운 전처리·분석과 DB 측정을
겹치지 않는다. 최종 원시 증거 검증 뒤에만 해당 단계의 완료를 인정한다.

CPU/RAM/I/O는 약 1초 간격 Docker 표본으로 기록한다. 이를 연속 관측한 정확한 peak라고
부르지 않는다. 질의 지연은 기존처럼 search 호출만 측정하고, 검사·워밍업·가시성/인덱싱
대기·쓰기 확인·클라이언트 직렬화 비용을 구분한다.

1차 지표는 최종 Recall@100의 fresh 대비 차이와 한 번/5회 대응 경로 차이다. 시점별·집단별
곡선은 탐색 분석으로 구분한다. 질의별 paired bootstrap과 fresh 3회 범위를 보존하되,
적은 데이터 seed 수·공유 코퍼스·다중 비교를 무시한 동등성 또는 제품 순위 주장은 하지 않는다.
