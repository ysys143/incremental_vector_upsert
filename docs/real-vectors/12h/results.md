# 공개 벡터 증분 갱신 실험 결과 — 승인된 12시간 범위

## 완료와 핵심 관측

승인된 66개 이력, 이력 측정 316회, fresh 구축 138회, 필터 64조건,
추가 ef 24조건을 모두 실행했다. 총 542개 검색 조건, 평가 질의 190,000건이다.
워밍업·스모크·튜닝 질의는 이 평가 질의 수에 포함하지 않는다.
native Dagster 233개 작업이 모두 성공했고, 독립 감사에서 원시 증거와 완료 수를 확인했다.

- 고정 T0: **2026-10-26 19:55:05 KST**.
- 측정·native 집계 완료: **2026-10-27 00:51:01 KST**, T0부터 **4시간 55분 56초**.
- 고정 마감: **2026-10-27 07:55:05 KST**. 후속 집단 분석·검증·이 보고서도 같은 기한에 포함한다.
- 정본: `real-results/twelve-hour-20261026-03`. 이전 실패·중단 이력을 성공 수치에 합치지 않았다.

현재 표본에서 확인한 내용은 다음과 같다.

1. 단순 삽입 후 Recall이 내려간 경우에도 동일 최종 데이터의 fresh와 차이가 작았다.
   데이터 증가에 따른 검색 난도 변화와 갱신 이력의 효과를 구분해야 한다.
2. MS MARCO의 50회 churn·같은 ID upsert에서 pgvector는 fresh 대비 각각
   **−0.994%p, −1.433%p**였다. Qdrant는 같은 비교에서 **+0.147%p, +0.104%p**였다.
3. 같은 최종 데이터의 한 번/5회 비교에서 삽입만의 차이는 작았고,
   삭제·churn·upsert는 이 표본에서 대체로 5회 분할 쪽의 Recall이 높았다.
4. 필터가 비어 있지 않은 56조건의 Recall@10/100은 모두 100%였다.
   PostgreSQL은 실제로 메타데이터 인덱스 기반 정확 검색을 사용했다.
   이 수치로 필터 HNSW의 열화가 없다고 결론낼 수 없다.

이 결과는 로컬의 5천–2만 벡터 탐색 실험이다. 제품의 보편적 순위나 대규모 안정성을
검증한 결과로 확장하지 않는다. 전체 조건의 수치와 구간은 아래 원시 집계 링크에 남겼다.

## 데이터·구성·비교 방법

| 항목 | 실행 조건 |
|---|---|
| 공개 임베딩 | MS MARCO–SimANS, Wikipedia–Cohere |
| 벡터 | 원본 768차원 float32, 내적(IP), 새 임베딩 생성·차원 축소 없음 |
| 활성 데이터 | 초기 10,000개; 삽입 후 20,000개; 삭제 후 5,000개; 교체 중 10,000개 |
| 기본 seed | 두 데이터셋 모두 11; MS MARCO의 일부 경로만 29 |
| 질의 | 초기·중간은 고정 200개; 최종·fresh는 같은 600개 |
| fresh | 최종 상태별 독립 구축 3회; 중간 시점 fresh는 승인 범위에서 제외 |
| 자원 | DB별 2 CPU·4GiB, DB 동시 실행 1개, 동일 로컬 호스트 |
| 버전 | PostgreSQL 17.11 / pgvector 0.8.7, Qdrant 1.17.1; 이미지 digest 고정 |
| 쓰기 관측 | 매 wave ACK·안정화·전체 ID/벡터/버전 검증; 50회 이력도 검색 생략 wave의 상태 검증 수행 |

| 데이터 | DB | M | efConstruction | 본 실험 검색 ef |
|---|---|---:|---:|---:|
| MS MARCO | pgvector | 16 | 100 | 1000 |
| Wikipedia | pgvector | 16 | 100 | 512 |
| 두 데이터셋 | Qdrant | 48 | 300 | 256 |

이 설정은 사전 후보 탐색에서 선택하고 초기·성장·삭제·교체 calibration 상태에서
Recall@10/100 ≥99%를 다시 확인했다. 본 평가 결과에 맞춰 재튜닝하지 않았다.
제한된 탐색에서 고른 설정이며 각 DB의 전역 최적 튜닝을 증명한 것은 아니다.

PostgreSQL 초기 적재는 COPY 후 HNSW 생성·ANALYZE다. 새 ID 삽입은 기존 HNSW를
유지한 COPY, 같은 ID 교체는 staging COPY와 ON CONFLICT UPDATE를 사용했다.
Qdrant는 `wait=true` 쓰기 후 인덱싱 안정화까지 확인했다.
외부 배치 경계에는 안정화·검증이 포함된다. 한 번/5회 차이를 HTTP 요청 크기만의
효과로 해석하지 않는다.

주 지표는 **같은 최종 벡터·ID·버전·질의·설정에서 inc Recall − fresh 3회 평균 Recall**이다.
시간 변화는 동일한 200질의에 대응시켜 계산한다. 최종 600질의 평균과 초기 200질의
평균을 직접 빼지 않았다. 신뢰구간은 질의별 차이의 2,000회 bootstrap이며,
데이터셋·구축 seed 전체의 불확실성이나 다중 비교를 보정한 검정은 아니다.

## 1. 삽입 뒤 품질 변화와 fresh 비교

10,000개에서 같은 신규 10,000개를 2,000개씩 5회 삽입한 seed 11 결과다.

| 데이터 / DB | 시간 변화: 공통 200질의 ΔR@100 (%p) | 최종 600질의 inc R@100 (%) | fresh 평균 (%) | inc−fresh (%p) |
|---|---:|---:|---:|---:|
| MS MARCO / pgvector | −0.205 | 99.720 | 99.696 | +0.024 |
| MS MARCO / Qdrant | −0.695 | 98.940 | 98.985 | −0.045 |
| Wikipedia / pgvector | −0.235 | 99.723 | 99.726 | −0.003 |
| Wikipedia / Qdrant | −0.220 | 99.713 | 99.706 | +0.008 |

특히 MS MARCO/Qdrant는 시간에 따른 하락보다 최종 inc−fresh 차이가 훨씬 작았다.
따라서 −0.695%p 전체를 증분 구축 이력으로 인한 손실로 볼 수 없다.
본 설정에서 20,000개 데이터의 검색이 초기보다 어려워진 효과가 섞여 있다.
그래프 연결을 직접 계측하지 않았으므로 이 설명은 대조 실험에 따른 해석이다.

## 3. 삭제·교체 및 50회 갱신

짧은 경로에서도 pgvector의 fresh 대비 손실이 나타났다. 한 번에 50%를 삭제했을 때
MS MARCO −0.088%p, Wikipedia −0.252%p였으며, 5회 분할에서는 각각
−0.023%p, −0.072%p였다. 한 번의 churn·같은 ID upsert 역시 두 데이터셋에서
fresh보다 낮았고, 5회 분할에서는 그 차이가 작아졌다. 전체 값은 66개 이력 표에 있다.

50회 조건은 MS MARCO seed 11에서 매회 1,000개를 변경하고 활성 크기 10,000개를
유지했다. 누적 변경은 50,000개이며 최종 데이터는 각 fresh와 일치한다.

| DB / 50회 경로 | 최종 inc R@100 (%) | fresh 3회 범위 (%) | inc−fresh (%p) | 95% 질의 bootstrap (%p) |
|---|---:|---:|---:|---:|
| pgvector / churn | 98.968 | 99.9617–99.9633 | −0.994 | [−1.087, −0.901] |
| pgvector / 같은 ID upsert | 98.520 | 99.9533–99.9533 | −1.433 | [−1.552, −1.312] |
| Qdrant / churn | 99.698 | 99.5483–99.5550 | +0.147 | [+0.089, +0.202] |
| Qdrant / 같은 ID upsert | 99.692 | 99.5850–99.5900 | +0.104 | [+0.048, +0.163] |

pgvector의 Recall@10 손실도 churn −0.250%p, upsert −0.350%p였다.
공통 200질의의 초기 대비 최종 R@100 변화는 pgvector −0.945/−1.425%p,
Qdrant +0.175/+0.110%p였다. pgvector churn은 25회 이후 계속 단조 하락한 것은 아니다.
갱신 횟수에 따른 전체 경로는 `trajectories.json`에 보존했다.

이 결과는 현재 구현의 갱신 이력에 따른 차이를 보여준다. 삭제 노드 연결 복구,
자동 유지보수, 세그먼트 구성 중 무엇이 원인인지는 직접 분리 측정하지 않았다.
Qdrant의 양수 차이도 일반적인 개선 보장이나 pgvector보다 항상 우수하다는 뜻이 아니다.

### 대조군

읽기 전용 50단계 대조군의 inc−fresh는 두 DB·두 데이터셋에서 약 0이었다.
pgvector의 같은 ID·같은 벡터 및 메타데이터 변경도 약 0이었다.
Qdrant/MS MARCO에서는 같은 벡터 쓰기 +0.103%p, 메타데이터 변경 +0.126%p가 관측됐다.
내용이 같더라도 쓰기·유지보수 이력이 결과를 바꿀 수 있음을 보여주며, 그 내부 원인은
이번 계측만으로 확정하지 않았다. 기존 벡터를 새 ID로 재삽입한 경로도 별도로 유지했다.

## 4. 신규 집단의 상대적 위치

MS MARCO에서 초기 벡터 512개를 고정 anchor로 삼고 후보별 최대 내적의 상·하위
10,000개를 near/far로 정했다. 각각 2,000개씩 5회 추가했다.
이는 의미적 거리나 그래프 위상을 독립 통제한 실험이 아니다.

| 신규 집단 | 최대 anchor IP 중앙값 | 벡터 norm 중앙값 | 표본 100개의 exact 기존 이웃 비율 |
|---|---:|---:|---:|
| near | 67.627 | 10.161 | 25.6% |
| far | 58.519 | 9.665 | 50.5% |

내적과 norm이 함께 달라졌고 기존 이웃 비율도 직관적인 거리 순서와 같지 않았다.
따라서 near/far 이름만으로 연결성의 좋고 나쁨을 판단할 수 없다.

| DB / 신규 집단 | 최종 inc R@100 (%) | fresh 평균 (%) | inc−fresh (%p) | 95% 질의 bootstrap (%p) |
|---|---:|---:|---:|---:|
| pgvector / near | 99.700 | 99.701 | −0.001 | [−0.013, +0.012] |
| pgvector / far | 99.772 | 99.767 | +0.004 | [−0.008, +0.017] |
| Qdrant / near | 98.682 | 98.517 | +0.165 | [+0.071, +0.258] |
| Qdrant / far | 99.132 | 99.228 | −0.096 | [−0.174, −0.022] |

Qdrant에서는 near의 절대 Recall이 더 낮지만 inc−fresh는 더 높았다.
신규 집단 자체의 검색 난도와 갱신 경로의 차이를 분리해야 하는 사례다.

집단별 표본 수는 near에서 기존/신규/혼합 질의가 **32/141/427개**,
far에서 **297/13/290개**다. far의 신규 집단 질의 13개만으로 안정적인 집단 결론을
내릴 수 없다. 이 집단은 exact top-10 중 변경된 ID·벡터의 비율로 정의했으며,
공간 경계를 직접 검출한 라벨이 아니다. 50회 교체 최종 시점은 600질의 모두
변경된 이웃 집단에 들어가므로 기존/경계 집단 간 비교가 불가능하다.
빈 집단도 생략하지 않고 n=0, Recall=N/A로 보완 보고에 기록했다.

## 5. 필터·선택도·카디널리티

MS MARCO 10,000개에 고정 ID별 메타데이터를 붙이고 같은 ID 벡터 5,000개를
5회 교체했다. 각 조건은 200질의, 초기/최종 × inc/fresh × 두 DB로 총 64조건이다.
필터 추가 측정은 fresh 첫 반복에만 실행했으며 필터 결과 자체의 3회 반복은 아니다.

| 필터 | 조건 | 후보 수 / 전체 | PostgreSQL 경로 | Qdrant 경로 |
|---|---|---:|---|---|
| F1 | cardinality 10, equality | 1,000 / 10% | 메타데이터 인덱스 정확 검색 | HNSW |
| F2 | cardinality 1,000, IN 10값 | 100 / 1% | 동일 | HNSW |
| F3 | cardinality 1,000, equality | 10 / 0.1% | 동일 | HNSW |
| F4 | 초기 공간 투영과 상관된 label | 10 / 0.1% | 동일 | HNSW |
| F5 | 편향 분포의 head label | 1,000 / 10% | 동일 | HNSW |
| F6 | 복합 조건 | 1 / 0.01% | 동일 | native filtered plain 또는 mixed |
| F7 | 빈 조건 | 0 / 0% | 동일 | native filtered plain 또는 mixed |
| F8 | unique rank 범위 | 100 / 1% | 동일 | HNSW |

후보가 있는 56조건은 Recall@10/100 모두 100%, 빈 8조건은 빈 결과가 맞았고
Recall은 N/A다. 후보 수가 k보다 작으면 분모를 min(k, 후보 수)로 사용했다.
PostgreSQL의 **enable_seqscan=off**와 인덱스 실행 계획을 확인했다.
무필터 검색은 HNSW 경로를 강제 검증했고, 필터에서는 승인된 btree 기반 정확 검색을
별도 분류했다. Qdrant도 요청의 exact=false뿐 아니라 telemetry의 실제 검색 경로를 확인했다.

이 필터 표는 현 규모에서의 기능·품질 검증이다. 특히 PostgreSQL 필터 검색의 HNSW
품질 저하를 검증한 표가 아니다. 메타데이터는 통제용 인공 label이며 실제 업무 label의
분포·벡터와의 상관관계를 대표하지 않는다.

## 6. 높은 ef가 가리는 차이

추가 24조건은 MS MARCO seed 11의 초기/5회 upsert 최종 × inc/fresh × ef 3개 × 두 DB다.
다음은 최종 상태의 고정 200질의 결과다. fresh는 추가 측정을 수행한 첫 구축이다.

| DB | ef | inc R@100 (%) | fresh R@100 (%) | inc−fresh (%p) |
|---|---:|---:|---:|---:|
| pgvector | 100 | 87.040 | 88.690 | −1.650 |
| pgvector | 256 | 96.515 | 97.525 | −1.010 |
| pgvector | 1000 | 99.930 | 99.975 | −0.045 |
| Qdrant | 100 | 96.700 | 95.900 | +0.800 |
| Qdrant | 256 | 99.695 | 99.625 | +0.070 |
| Qdrant | 512 | 99.990 | 99.980 | +0.010 |

높은 Recall 설정 한 점에서 작은 차이가 보이더라도 낮은 탐색 예산에서는 차이가 커질 수 있다.
이는 50회 이력의 ef sweep이 아니며, 50회 결과가 ef 조정만으로 회복된다는 근거는 아니다.
각 조건의 p95도 `ef-curves.json`에 있다. PostgreSQL은 이 클라이언트 경로에서 대부분
약 17ms, Qdrant는 약 3–6ms였다. 지속 psql과 HTTP의 서로 다른 전송 경로 및 로컬
공유 호스트 비용이 포함돼 있으므로 이를 DB 엔진 자체 지연의 공정한 순위로 해석하지 않는다.

슬롯을 적용했다. DB 측정은 하나씩 실행했고, 준비 계산은 DB가 쉬는 구간에서만 병렬화했다.
독립 완료 감사는 lease 취득부터 native check 종료까지 실제 구간이 겹치지 않았음을 확인했다.
최초 barrier 결함과 실행 순서 수정은 준비 단계에서 처리했고 원래 결과·소스·T0를 보존했다.
수정 과정과 재사용 근거는 [실행 기록](execution.md)에 있다.

| 완료 검사 | 결과와 근거 |
|---|---|
| 233개 native 작업 및 partition별 검사 | `independent-completion-audit.json`: PASS |
| 전체 조건·19만 질의·원시 해시·DB 독점 | 같은 독립 감사: PASS |
| 모든 이력 집단별 수·동일 데이터 대응 | `cohort-supplement/supplement-receipt.json`: PASS, 316시점·66최종·89,600질의 |
| 오류 주입 및 보고 보완 검사 | `postmeasurement-tests.json`: 14 PASS, 실패·오류·skip 0 |
| 실제 native 동결 소스 변경 거부 | `source-gate-diagnostic/receipt.json`: 정상 source 성공, 변경 source 의도된 실패, worker 미시작 |
| 작업 종료·자원 정리 | controller COMPLETE_SELECTED_SCOPE, guardian RECONCILED, 활성 lease 0 |

오류 주입에는 잘못된 oracle 대응 열, query 변경, PG Seq Scan, Qdrant의 실제 기록된
exact/fallback telemetry, 결과 누락, 집단 라벨·표본 누락을 포함한다.
소스 변경 검사는 별도의 작은 fixture 캠페인에서 수행했으며 그 의도된 실패는 본 실험
실패 수와 구분한다. 사전의 실제 부모 사망·timeout·cleanup 검증도 실행 기록에 연결했다.

완료 후 공간 점검에서 호스트 여유 약 **36.3GiB**, `real-results/` 전체 소유 파일
논리 크기는 약 **3.96GiB**였다. 후자는 이전 실험 증거도 포함하며 Docker 디스크 이미지나
전체 호스트 사용량과 같지 않다. 활성 DB 예약은 해제됐다. 이전 실패 컨테이너·볼륨은
격리 증거로 보존했다. 클라우드 인스턴스나 유료 API를 사용하지 않았다.

## 해석의 한계와 후속 연구

이번 승인 범위는 완료했다. 초기 전체 연구는 후속 과제가 남아 있다.

- 최대 20,000개, 768차원 두 데이터셋 결과다. 수백만·수억 개에서의 세그먼트 병합,
  메모리 압박, 삭제 누적과 같은 거동을 검증하지 않았다.
- 기본 seed 11, 일부 seed 29만 사용했다. 600질의 bootstrap을 독립 데이터·구축 seed
  반복으로 취급하지 않는다. 작은 양수·음수 차이를 제품 전반의 우열로 확정하지 않는다.
- 동일 최종 데이터 fresh는 갱신 이력의 비교 대조다. 실제 그래프 연결·LID·위상을
  직접 분석하거나 내부 유지보수 효과를 각각 분해하지 않았다.
- 클러스터/공간순 삽입, bridge 집단, 집중 삭제·교체, 온라인 동시 쓰기·읽기,
  강제 정리·회복, 전체 필터 요인 교차와 추가 seed는 승인된 연기 목록에 남는다.
- 필터 라벨은 고정했다. 메타데이터 변경과 필터 품질의 상호작용은 별도 후속 범위다.
- 추가 ef는 일부 경로의 진단이다. 모든 상태의 파레토 곡선이나 동일 지연시간에서의
  제품 간 품질 비교를 완성하지 않았다.

후속 계획은 [승인 계획의 연기 목록](plan.md)을 기준으로 사용자와 정한다.
이번 결과에서 우선 검토할 현상은 pgvector의 50회 교체 손실, 낮은 ef에서의 이력 차이,
그리고 near/far 집단에서 절대 Recall과 inc−fresh 부호가 다른 현상이다.
