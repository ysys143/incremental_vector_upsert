# 공개 벡터 증분 갱신 실험 — 12시간 실행 계획

작성: 2026-10-26. 완료 갱신: 2026-10-27. **상태: 승인된 12시간 범위 완료.**

[최종 결과와 해석](results.md)에 관측값·한계·전체 증거를 기록했다.
기존 전체 연구의 연기 항목은 아래 목록대로 미완이며, 이번 완료에 포함하지 않는다.

승인 지시: `12시간 계획을 완수.` / `승인한다.`
T0는 2026-10-26 19:55:05 KST, 최종 기한은 2026-10-27 07:55:05 KST다.
승인 당시 문서·목록과 해시, 시작 시각은
`real-results/twelve-hour-20261026-01/authorization.json` 및 `approved-plan.md`,
`approved-matrix.json`에 보존했다. 현재 구현·검증·실행 기록은

요청: “12시간 이내 가능한 플랜으로 갱신.”, “계획 문서 갱신하고 승인받아.”

이번 승인 대상은 아래의 축소된 실험표, 설정, 측정 시점, 시간 예산이다.
12시간은 승인 후 구현·실행을 시작한 T0부터 보고서 생성까지의 경과 시간이다.
현재 문서를 편집한 시간과 기존 실험에서 소비한 시간은 새 실행 시간에 포함하지 않고
각각 별도 이력으로 남긴다. 사용자 승인과 `12시간 계획을 완수.` 지시를 함께 적용했다.

실행 목록 정본은 [real-vector-12h-matrix.json](matrix.json)이다.
이는 **계획용 목록**이며 현재 러너가 읽어 실행하는 설정 파일은 아니다.
기존 348건 계획과 미승인 48시간안은
[개정 전 아카이브](../../archive/real-vector-before-12h-20261026/)에 보존했다.

## 목표와 해석 범위

두 실제 공개 임베딩에서 삽입·삭제·동일 ID 교체가 검색 품질에 미치는 영향을,
현재 데이터로 재구축한 인덱스와 비교한다. 같은 데이터의 한 번 대 5회 삽입,
반복 갱신, 벡터를 바꾸지 않는 대조군을 유지한다.
12시간 안에는 기본 비교와 작은 공간·필터 탐색 실험을 마친다.
기존 전체 요인 실험을 완료했다고 주장하지 않는다.

실측된 기존 기본 실험의 잠정 비용은 4~6일이었다. 아래 안은 이력 수,
50회 경로의 관측 빈도, 중간 fresh 수를 줄이고 구축 비용이 낮은 튜닝 후보를 사용한다.
**전체 12시간 완주를 실제로 검증한 상태는 아니다.** 양 DB의 비용 스모크가 입장 조건이며,
불가능한 비용이 나오면 자동으로 항목을 더 빼지 않고 그 근거를 보고한다.

| 항목 | 승인 대상 값 |

| 크기 | 초기 10,000, 삽입 최종 20,000, 삭제 최종 5,000 |

| 자원 | 각 DB 2 CPU·4GiB, 전체 DB 측정 슬롯 1개 |
| 기본 반복 | 두 데이터셋 모두 seed 11 |

200개를 결과를 보기 전에 선정해 모든 대응 경로에 공통 사용한다.
초기·중간과 최종의 시간 변화는 같은 200개 부분집합에서도 계산하고,
최종 inc–fresh 비교에는 600개를 모두 사용한다.

## 실험표: 총 66개 시나리오

### 기본 비교 60개

두 데이터셋 × 두 DB × seed 11에서 다음 12개씩, 총 48개를 실행한다.

| 조건 | 시나리오 수 / 데이터셋·DB | 변경 |
|---|---:|---|
| 100% 신규 삽입 | 2 | 10,000개 한 번 / 2,000개씩 5회 |
| 50% 삭제 | 2 | 5,000개 한 번 / 1,000개씩 5회 |
| 50% 삭제·새 ID 삽입 | 2 | 5,000개 한 번 / 1,000개씩 5회 |
| 50% 동일 ID 벡터 교체 | 2 | 5,000개 한 번 / 1,000개씩 5회 |
| 같은 벡터를 새 ID로 재삽입 | 1 | 1,000개씩 5회 |
| 동일 ID·동일 벡터 쓰기 | 1 | 1,000개씩 5회 |
| 메타데이터만 변경 | 1 | 1,000개씩 5회 |
| 쓰기 없는 대조군 | 1 | 50회 단계, 지정 시점에서 검색 |

MS MARCO × 두 DB × seed 11에는 무작위 대상 churn과 upsert를 각각
1,000개씩 **50회** 수행하는 4개 시나리오를 추가한다. 한 이력에서 새 벡터의
source row를 재사용하지 않는다. 50회 갱신을 5회로 축약하지 않는다.

MS MARCO × 두 DB × seed 29에는 삽입 한 번/5회, churn 5회, upsert 5회의
8개 시나리오를 추가한다. 총 **48 + 4 + 8 = 60개**다.
Wikipedia와 나머지 조건은 seed 하나이므로 데이터 순서에 대한 반복 검증 범위가 제한된다.

한 번/5회 대응 경로는 같은 초기 physical snapshot에서 시작하고,
대상 ID·벡터의 전체 순서와 최종 원장을 일치시킨다.

### 공간 조건 4개

MS MARCO, seed 11에서 초기 집합에 가까운 신규 집합과 먼 신규 집합을 각각
10,000개씩 5회로 나눠 삽입한다. 두 조건 × 두 DB = **4개**다.
기본 실험의 무작위 삽입 5회가 비교 기준이다.

초기 집합에서 고정 seed로 512개 기준 벡터를 뽑는다. 사용 가능한 원본 후보의
`max(inner_product(candidate, reference))`를 계산해 상위·하위 각 10,000개를 선택한다.
튜닝 문서·초기 집합·중복 벡터를 제외하고, 입력 선택과 질의는 ANN 결과와 독립적으로 고정한다.
각 신규 집합 내부 순서는 고정 무작위 순서로 둔다. 원본 row와 벡터는 변형하지 않는다.

이 규칙은 **IP 유사도에 따른 집합 선택**이다. 의미적 거리나 그래프 위상을 완전히
통제했다는 주장을 하지 않는다. 벡터 norm, 실현 유사도 분포, 표본 exact 교차 이웃 비율을
함께 기록하고, 최종 데이터 난도는 각 집합의 fresh 대조군으로 분리한다.

### 필터용 갱신 2개와 검색 조건 64개

MS MARCO, seed 11에서 필터 라벨을 처음부터 가진 별도 집합을 만들고,
동일 ID의 벡터 1,000개씩 5회 교체한다. 두 DB에서 **2개** 시나리오다.
필터 라벨은 ID에 고정하고 벡터 교체 중에는 바꾸지 않는다.
필터 라벨·인덱스를 도중에 추가해 기존 그래프와 섞지 않는다.

| 조건 | 카디널리티 | 통과 비율 | 목적 |
|---|---:|---:|---|
| F1: 균등 라벨 일치 | 10 | 10% | 넓은 필터 |
| F2: 균등 라벨 10개 IN | 1,000 | 1% | 중간 선택도 |
| F3: 균등 라벨 일치 | 1,000 | 0.1% | 후보 수 < k |
| F4: 초기 공간과 상관된 균등 라벨 일치 | 1,000 | 0.1% | 필터·벡터 상관 |
| F5: 빈도 편향 라벨의 지정 head 값 | 1,000 | 10% | 편향 분포 |
| F6: 라벨과 순위의 복합 조건 | 1,000 | 0.01%, 1개 | 극소 후보 |
| F7: 존재하지 않는 라벨 | 1,000 | 0%, 0개 | 빈 결과 |
| F8: 순위 범위 | 10,000개의 고유 순위 | 1%, 100개 | 범위 조건·후보 ≥ k |

라벨은 자연 메타데이터가 아닌 통제용 값이다. 균등 라벨은 seed로 섞은 ID 순위를
동일 크기로 분할한다. 공간 상관 라벨은 초기 벡터의 고정 투영 순위를 동일 크기로
분할하고 이후 고정한다. head-heavy 라벨은 지정 head 1,000개, 나머지 9,000개를
999개 값에 배정해 모든 값이 존재하게 한다. 고유 순위는 ID의 별도 고정 순열이다.
술어와 실제 후보 수, 갱신 전후 상관의 실현값을 기록한다.

8조건 × 초기/최종 2상태 × inc/fresh 2종 × DB 2개 = **64개 검색 조건**이다.
각 200질의이며 fresh 3회 중 repeat 0에만 추가 필터 측정을 수행한다.
따라서 필터 결과 자체에는 독립 fresh 3회 반복이 없다.
정답은 현재 상태에서 필터를 만족하는 집합의 exact top-k이며,
분모는 `min(k, eligible_count)`다. 후보 0개는 Recall N/A와 빈 결과 정확성으로 보고한다.

PostgreSQL은 필터에서도 seqscan off를 유지하고 실제 계획을 보존한다.
Qdrant는 `exact=false` 요청과 실제 ANN/plain 경로를 함께 기록한다.
필터에서 엔진이 exact 경로를 선택한 결과는 제품의 필터 검색 동작으로 별도 표시하고,
HNSW 품질 측정으로 승격하지 않는다. 무필터 실험의 fallback 금지 조건은 유지한다.

## 측정 수와 시점

1회·5회 경로는 초기와 모든 갱신 뒤에 측정한다.
50회 경로와 read-only 대조군은 **0·1·5·10·25·50회**에 검색 품질을 측정한다.
측정하지 않는 wave도 쓰기 ACK, 정상 인덱싱 안정화, 현재 ID·벡터·버전 확인을 거친다.
검색을 생략한 wave의 Recall 값을 보간해 실제 관측값으로 표시하지 않는다.
read-only는 같은 단계 수의 대조군이며 갱신 경로와 경과 시간이 같지는 않다.

중간 상태의 fresh는 이번 실행에서 제외한다. 초기 상태는 read-only 경로의 최종 원장과
같아 3회 fresh가 포함된다. 최종 상태당 fresh 3회는 유지한다.
기본 60개에서 **114회**, 공간 조건에서 12회, 필터 초기·최종에서 12회로 총 **138회**다.
기본 114회는 이미 준비된 실제 원장 해시로 중복을 제거해 계산했다.
공간·필터 입력은 구현 시 동결하며 선언한 그룹 수와 실제 실행 목록을 다시 검증한다.

MS MARCO seed 11의 초기와 upsert-5 최종 상태에는 추가 검색 ef 곡선을 측정한다.
PostgreSQL은 100/256/1000, Qdrant는 100/256/512를 사용한다.
3 ef × 2상태 × inc/fresh 2종 × DB 2개 = **24개**, 각 200질의다.
고정 설정 결과를 먼저 수집한 뒤 수행하고 비용을 별도 기록한다.

| 구분 | 측정 횟수 | 측정 질의 합계 |
|---|---:|---:|
| 66개 시나리오의 무필터 이력 | 316 | 89,600 |
| fresh 구축·무필터 측정 | 138 | 82,800 |
| 필터 조건 | 64 | 12,800 |
| 추가 ef 곡선 | 24 | 4,800 |
| **합계** | **542** | **190,000** |

워밍업, EXPLAIN, 정답 검증, 스모크 전용 질의는 위 질의 수와 별도다.
각 point는 그 point의 질의 집합으로 워밍업한다. 최초·중간 200개와 최종 600개의
지연을 직접 동일 반복수의 벤치마크로 취급하지 않는다.

## 설정: 기존 품질 검증을 통과한 후보 활용

이미 완료한 calibration 76개 작업을 다시 모두 실행하지 않는다.
네 상태에서 Recall@10/100 ≥99%를 통과한 기존 결과 중 아래 후보를 새 스모크로 재확인한다.

| 데이터셋 / DB | M | ef_construction | 검색 ef | 기존 네 상태의 최소 Recall@100 |
|---|---:|---:|---:|---:|
| MS MARCO / pgvector | 16 | 100 | 1000 | 99.735% |
| Wikipedia / pgvector | 16 | 100 | 512 | 99.755% |
| MS MARCO / Qdrant | 48 | 300 | 256 | 99.005% |
| Wikipedia / Qdrant | 48 | 300 | 256 | 99.685% |

PostgreSQL은 이전의 검색 지연 최소 후보에서 **구축 비용이 낮은 Pareto 후보**로 바꾼다.
이는 전체 실행 비용을 고려한 제한된 최적화이며 전역 최적 설정이라는 주장이 아니다.
구축 시간은 기존 네 상태 합계가 MS MARCO 147.30→20.89초,
Wikipedia 145.01→22.94초였지만, 반복 삽입 시간의 단축 폭은 아직 검증 전이다.
스모크를 통과한 설정은 본 이력 동안 동결한다. 중간에 파라미터를 바꿔 실험을 이어가지 않는다.
이전 M=64 실패 이력의 부분 결과는 새 M=16 이력에 합치지 않는다.

## 시간 예산: 총 12시간

| 단계 | 상한 |
|---|---:|
| 종료·정리 결함 수정, 실행 목록 구현, 입력 재사용 검증, 양 DB 비용 스모크 | 2시간 |
| 무필터 이력·공간 조건·fresh·ef 곡선 | 7시간 |
| 필터 갱신·검색 | 1시간 |
| 원시 검증·대응 분석·보고서 | 30분 |
| 변동·오류 대응 여유 | 1시간 30분 |
| **총합** | **12시간** |

이 시간은 배정 예산이다. 실제 검증 전 종료 시각을 확정값으로 말하지 않는다.
T0+12시간의 단일 기한을 controller·driver·worker·watchdog·guardian에 동일하게 전달하고,
재개·새 shard·스모크 재시도로 초기화하지 않는다. 기존 4시간 제한의 모든 적용 지점을
정리하고 짧은 만료 fixture로 검증한다. 12시간 기한만 늘린 채 기존 348건을 실행하지 않는다.

첫 2시간 안에 두 DB 각각에 대해 200/600질의, COPY/업데이트, snapshot 복원,
5k/10k/20k fresh 구축과 native 시작·종료 비용을 측정한다.
50회 MS MARCO 경로는 초기 비용 스모크와 겸해 먼저 양 DB를 수행하고,
같은 동결 조건의 native SUCCESS·필수 검사가 있으면 해당 선언 시나리오의 완료로 인정한다.
중간 단계만 성공한 결과를 완주로 재사용하지 않는다.

예측은 원장에 있는 실제 남은 쓰기 수·point 수·fresh 수와 단계별 관측 비용으로 계산한다.
동일 작업의 표본이 5개 미만이면 최대 관측값, 그 이상이면 p90을 쓰되,
전체 예상 잔여 비용에 20% 여유를 더한다. 이는 통계적 완료시간 보장이 아니다.
50회 경로는 후반 비용도 포함하며 다른 설정의 과거 경로를 새 설정의 노후 표본으로 쓰지 않는다.
스모크를 포함한 예상 완료가 **T0+10시간 30분 이내**여야 본 실행을 계속한다.
기준을 넘으면 현재 비용·충돌 항목을 보고하고 사용자 판단을 기다린다.
매개변수·필수 조건을 자동 축소하거나 새 기한을 부여하지 않는다.

실행 순서는 공통 준비 → 양 DB 비용 스모크 → 대응하는 짧은 시나리오 → 장기 잔여 경로
→ 공간 → 필터 → 집계다. 한 DB의 장기 작업만 먼저 몰아 Qdrant 비용을 모르는 상태를
반복하지 않는다. just-dag-it에서 사용한 native Dagster 의존성·자원 슬롯·검사 차단을
계승한다. CPU 준비 최대 2개는 DB가 쉬는 구간에만 병렬화하고, DB 실행은 순차다.

## 재시작 전 해결할 실패 조건

현재 기존 캠페인은 중단돼 있고 DB는 49번째 wave의 삭제만 반영된 상태다.
[실패 조사](../baseline-failure-20261026.md)를 실행 전제에 포함한다.

1. 장시간 작업을 대화 세션의 자식 수명에 의존하지 않는 로컬 실행 소유자에 맡긴다.
   일회성 사용자 실행 서비스 등 실제 사용 가능한 수단을 확인하고, launcher 종료 후
   짧은 worker가 지속되는 경로를 시험한다. `start_new_session=True`만으로 해결됐다고 하지 않는다.
2. 실패 종료와 자원 정리 완료를 다른 상태로 기록한다. ended/failed 작업도 남은 소유 자원과
   cleanup receipt를 검사한다. 강제 종료를 주입해 lease·컨테이너·watcher 정리를 확인한다.
3. 조회 시 PID 생존·native 상태·원장을 대조한다. 죽은 controller의 RUNNING JSON을
   진행 중으로 보고하지 않고 ORPHANED/STOPPED_INCOMPLETE로 표시한다.
4. DELETE ACK와 COPY ACK를 각각 영속 기록하고, 부분 반영 시 자동 재전송하지 않는다.
   기존 9,000행 volume은 원장과 진단 증거를 보존해 격리한다. 새 실험은 검증된 초기 상태로 시작한다.
5. 실패 쓰기·timeout·부모 사망·늦은 출력 이후 완료 판정이 잘못 통과하지 않는지 검사한다.

위 항목의 실행 전 검증을 완료하고 본 실험을 시작했다.
구현·실제 실패 주입의 명령과 결과는 [실행 기록](execution.md)의
실행 전 확인 및 최종 완료 절에 있다. 승인 당시 미검증 상태는 보존된 원본에 남아 있다.

## 공간과 기존 증거

문서 갱신 시점 실측: 호스트 여유 약 55GiB, real-results 소유 파일 약 2.363GiB다.
새 영속 산출물 1.5GiB와 활성 DB/임시 파일 예약 2GiB를 별도로 잡으면 계획상 합계 약
5.863GiB로 기존 8GiB 상한 안이다. 이는 예상 예약이며 실제 바이트를 계속 계측한다.
원본 fbin, 입력 원장, 기존 oracle을 검증해 재사용한다. 새 전체 벡터 파일을 복제하지 않는다.
실패 증거를 삭제해 공간을 맞추거나 호스트 전체 cache/image prune을 하지 않는다.

## 기존 계획에서 미루는 항목

아래는 사용자가 승인한 12시간안의 명시적인 범위 변경이다.
이번 완료 기준에서 제외했으며, 장기 연구 요구는 미완으로 남긴다.
담당은 실험 구현 에이전트이며, 재검토 시점은 12시간 결과 보고 직후의 후속 계획 수립 때다.

| 기존 범위 | 이번 포함 | 미루는 조건과 이유 |
|---|---|---|
| D1–D3 정적·데이터 교차·기하 | 두 데이터셋, 제한된 ef 곡선, near/far 진단 | 전체 LID·그래프 위상 분석: 구현·계산 예산 |
| I1–I2 삽입 비율·배치 분할 | 100% 삽입의 한 번/5회 | 10/25/50% 삽입 교차: 시나리오 수 |
| I3 신규 집단 | 무작위·near·far | bridge 집단과 완전 교차: 입력 구조 검증 비용 |
| I4 삽입 순서 | 고정 무작위 순서 | 군집별·공간순 교차, 실제 시간순: 예산 및 자연 timestamp 부재 |
| I5 관찰 방식 | 매 wave 안정화, 장기 검색 시점 축소 | 연속 쓰기 대조군: 별도 유지보수 경로 비교 필요 |
| X1–X3 삭제 | 무작위 50% 한 번/5회 | 10/25%, 공간 집중 삭제: 교차 수 |
| C1–C5 churn·재삽입 | 짧은 한 번/5회, MS 무작위 50회, 동일 벡터 새 ID | 반복 집중·영역 교체·시간순·Wikipedia 50회: 예산 |
| U1–U5 upsert·대조군 | 짧은 한 번/5회, MS 무작위 50회, 동일 벡터·메타데이터 | 근/중/원거리 교체, hot 50회, Wikipedia 50회: 예산 |
| M1–M3 유지보수·회복 | 기본 정상 정책과 안정화 비용 | 쓰기 중단 후 회복·강제 정리 비교: 별도 개입 |
| M4 온라인 혼합 | 없음 | 동시성·시점별 oracle 검증 구현 비용 |
| M5 재튜닝 회복 | 고정 그래프의 추가 ef 곡선 | 재구축/재튜닝 전략의 회복 비용 비교 |
| F 필터 | 8개 고정 조건, 초기·최종 inc/fresh | 전체 요인 교차·필터 메타데이터 갱신; cardinality 100k는 현 N에서 불가 |
| seed 11/29/47 | seed 11 전체, MS 네 경로 seed 29 | seed 47와 나머지 seed 29: 반복 수 |
| 매 시점 fresh | 초기·최종 3회 | 중간 fresh: 구축 수 |

따라서 이번 결과는 탐색 실험이다. 집단별 표본 수·대응 차이·질의별 bootstrap 구간과
fresh 3회 범위를 보고하되, seed 하나/둘로 제품의 보편적 우열·동등성이나
희소한 0.1%p 수준 차이를 검증했다고 주장하지 않는다.
통계적 유의성에 따라 실험을 조기 중단하거나 좋은 결과만 골라 보고하지 않는다.
