# 공개 벡터 클러스터별 삽입 실험 계획

작성: 2026-10-27. 상태: **실행 지시 수신, G0 통과, 새 캠페인 시작**.

현재 상태와 실패·완료 판정은 [실행 기록](clustered/execution.md)을 따른다. 아래 설계 당시의
제안값은 새 run의 approved-plan/matrix 및 manifest에 동결했다. 승인 당시 원본은 run에 보존했다.

사용자 요청은 공개 임베딩을 클러스터링한 뒤 클러스터별로 삽입하는 후속 실험의 설계다.
사용자는 준비·튜닝·실행·보고를 포함한 **12시간 상한**에 동의했다. 이는 이 문서의
실험표·튜닝 수치와 실제 실행 전체를 승인한 것으로 해석하지 않았다. 이후 사용자의
`clustered-insertion-plan 완수.` 실행 지시에 따라 2026-10-27 새 캠페인을 시작했다.
병행 중인 저장소 구조 개편은 별도 작업이며, 새 실험은 개편의 실행 경로 검증 이후에 시작한다.

[계획용 실험표](clustered-insertion-matrix.json)는 경로와 수량을 검산하기 위한 명세다.
러너는 이 명세에서 별도의 동결 실행 manifest를 생성한다. 과거 캠페인·마감·receipt는 재사용하거나 갱신하지 않는다.

## 1. 사용자 목적과 연구 질문

사용자는 실제 제품의 증분 삽입에서 입력의 공간적 묶음과 배치 경계가 검색 품질에
어떤 차이를 만드는지 알고자 한다. 같은 최종 데이터에서도 결과가 달라지는지,
재구축과 검색 ef 증가 중 무엇으로 회복되는지를 구분한다.

1. 같은 신규 벡터를 클러스터별로 모아 삽입하면 무작위 순서보다 Recall이 낮아지는가?
2. 동일한 전체 순서를 한 번 또는 5회로 나누면 결과가 달라지는가?
3. 최종 평균에 가려진 기존·신규·경계 질의 또는 특정 클러스터의 손실이 있는가?
4. 변화가 현재 데이터의 검색 난도 변화인지, 같은 데이터의 fresh 대비 이력 차이인지?
5. 운영용 높은 ef에서 차이가 작아도 더 낮은 탐색 예산에서 차이가 나타나는가?

### 선행 관측과 이번 가설의 한계

- [합성 삽입 결과](../synthetic-insertion/results.md)에서 Qdrant의 bridge/ordered/5회
  경로는 최종 fresh 대비 평균 −5.810%p였다. 그 합성 공간을 실제 임베딩의 클러스터가
  재현한다고 가정하지 않으며, 이 감소 폭을 성공 기준으로 삼지 않는다.
- [이전 공개 벡터 결과](12h/results.md)의 단순 삽입은 fresh와 차이가 작았다.
  무작위 삽입과 anchor-IP near/far 집합 선택이었고, 이번 클러스터 순서 대조는 없었다.
- [Elliott·Clark 원문](https://arxiv.org/abs/2405.17813)은 HNSW의 삽입 순서와
  데이터 특성에 따른 Recall 변화를 다룬다. 제품별 결과나 이번 효과 크기를 예측하는 근거로 쓰지 않는다.
- 클러스터별 삽입은 입력의 기하학적 순서 조작이다. 실제 HNSW edge·연결 성분을 직접
  계측하지 않으므로, 품질 차이만으로 그래프 단절이라는 기전을 확정하지 않는다.

## 2. 고정 조건과 설계 결정

다음 수치는 설계 당시 제안했고, 사용자 실행 지시 이후 G0에서 동결했다. 총 12시간 상한과 로컬 실행을 유지한다.

| 항목 | 동결값 |
|---|---|
| 데이터 | 기존 검증 캐시의 MS MARCO–SimANS, Wikipedia–Cohere |
| 벡터·검색 거리 | 원본 768차원 float32, IP; DB 적재 벡터 변형 없음 |
| DB | pgvector HNSW, Qdrant HNSW; 이전 버전·이미지 digest를 확인해 고정 |
| 크기 | D0 10,000 + 신규 A 10,000 = 최종 20,000 |
| 반복 | 데이터·순서 seed 11, 29, 47; 각 seed의 네 경로는 같은 초기 physical snapshot |
| 신규 집합 클러스터 | K=5; 자연 클러스터 크기를 유지 |
| 평가 질의 | 고정 600개; 초기·중간에는 이 중 사전 고정 200개 |
| calibration | 평가와 겹치지 않는 문서·질의 200개, seed 7 |
| 운영용 품질 목표 | calibration의 지정 상태 모두 Recall@10/100 ≥0.99 |
| DB 자원 | DB별 2 CPU·4GiB, 실제 DB 측정 동시성 1 |
| 공간 | 매 작업 예약 후 호스트 여유 ≥10GiB, 새 작업의 소유 디스크 증가·예약 합계 ≤8GiB |
| 시간 | 실행 지시 후 T0부터 보고·정리까지 43,200초; 재시도·수정 시간 포함 |

두 DB에 같은 M이나 ef를 강제하지 않는다. 각 DB에서 제한된 사전 탐색의 품질·지연·구축
비용을 비교해 선택하고 평가 전에 동결한다. 절대적인 전역 최적 튜닝을 주장하지 않는다.
기존에 확보한 공개 벡터를 사용하며, 임베딩 생성·대규모 재다운로드·차원 축소는 하지 않는다.

## 3. 입력과 클러스터를 만드는 방법

### 3.1 평가 누출과 입력 동일성

- 먼저 source manifest, byte hash, 원본 row ID, 차원, dtype, 유한값을 검증한다.
- 기존 전역 calibration holdout을 보존한다. 평가 질의와 문서의 동일 벡터 중복도 제거한다.
- seed별로 D0와 A를 먼저 고정한다. 이후의 클러스터링은 **A만** 사용한다.
- DB·경로별 D0/A의 ID, source row, 원본 벡터, 메타데이터, 질의가 동일해야 한다.
- ID는 원본 row와의 동결 매핑으로 미리 정한다. 삽입 순서마다 ID를 다시 부여하지 않는다.
- 세 seed는 같은 공개 pool에서 뽑은 재표본이다. 겹침률을 기록하고, 서로 완전히 독립적인
  실제 서비스 데이터셋 세 개로 해석하지 않는다.

### 3.2 클러스터링 알고리즘

동결한 알고리즘은 A의 **복사본을 정규화한 spherical k-means, K=5**다. cosine 방향을 묶는
조작이며, DB가 검색하는 원본 IP 거리와 같다고 주장하지 않는다. 원본 norm과 방향 효과를
함께 기록한다. 원본 벡터를 정규화해서 DB에 저장하거나 centroid를 문서로 넣지 않는다.

- 초기화·동률 처리·centroid 재정렬 규칙을 코드와 manifest에 동결한다.
- 초기화 3회, 각 최대 50 iteration, 목적함수 상대 변화 허용치 1e-4를 적용한다.
  가장 좋은 clustering 목적함수를 선택하며 ANN Recall은 선택에 사용하지 않는다.
- 0 norm, NaN/Inf, 빈 클러스터, 5개 미만의 유효 centroid는 G1 실패다.
  실패를 숨기려고 K·데이터·seed를 자동 변경하지 않는다.
- 클러스터 ID는 최소 source row 순으로 정규화한다. 클러스터 간 순서는 별도의 동결
  seed permutation, 내부 순서도 고정 permutation이다. 가까운 순서라고 명명하지 않는다.
- 클러스터를 2,000개씩 강제로 균등 분할하지 않는다. 크기 n1…n5와 누적 경계를 기록한다.
- 클러스터 크기·centroid 유사도·내부 cosine·norm 분포와 기존 D0에 대한 IP를 기록한다.
  구분이 약한 클러스터도 숨기지 않는다. 공간 조작이 약하면 그 한계가 결론에 포함된다.

### 3.3 공간 진단과 질의 집단

데이터 진단은 고정한 문서 anchor 512개와 신규 표본 256개를 사용한다. 원본 IP의
기존/신규 교차 top-20 이웃 비율, 클러스터 내부 이웃 비율, norm 분포를 계산한다.
정규화 공간의 거리 진단과 원본 IP 진단은 별도 열에 보존한다.
표본 이웃 구조를 전체 DB HNSW의 conductance나 실제 edge로 부르지 않는다.

평가 질의는 ANN 결과를 보기 전에 고정하고 다음 집단을 **최종 exact 정답**으로 정한다.

- 최종 exact top-10 중 신규 이웃 비율 ≤0.2: 기존 중심; ≥0.8: 신규 중심; 나머지: 경계.
- 신규 이웃의 주된 클러스터별 집단과, 신규 이웃 중 최대 클러스터 비율 <0.6인 혼합 집단.
  신규 이웃이 없으면 별도 코드로 남긴다. 동률은 고정된 cluster ID로 처리한다.
- 고정 집단으로 시간 변화를 본다. 시점별 현재 이웃 집단은 별도 보조 분석으로만 기록한다.
- 집단별 질의 수가 30 미만이면 기술 통계와 n만 제시하고 그 집단의 유의성 판단은 보류한다.
  집단을 채우기 위해 평가 질의나 클러스터를 사후 교체하지 않는다.

이번 기본 비교에서는 D0에도 유사한 모드가 이미 있을 수 있다. 따라서 완전히 없던
새 의미 클러스터의 유입이나 임베딩 모델 교체를 검증했다고 해석하지 않는다.

## 4. 네 경로와 대조군

각 데이터셋·DB·seed 조합에서 아래 네 경로를 실행한다.

| 경로 | 신규 벡터 전체 순서 | 논리적 삽입 wave | 중간 측정 |
|---|---|---|---|
| M1 | A 전체 고정 무작위 순서 | 10,000개 한 번 | 없음 |
| M5 | M1과 완전히 같은 순서 | n1…n5의 5회 | 각 wave 후 |
| C1 | 클러스터별로 묶은 고정 순서 | 10,000개 한 번 | 없음 |
| C5 | C1과 완전히 같은 순서 | 각 클러스터 한 개씩 5회 | 각 wave 후 |

M5의 wave 크기를 C5와 일치시키므로, 자연 클러스터의 불균형을 배치 크기 차이와 혼동하지 않는다.
네 경로의 최종 원장은 동일하다. M1/M5, C1/C5는 전체 벡터 순서도 같다.
M5/C5의 중간 데이터 집합은 다르므로 그 시점의 Recall을 곧바로 순서 효과로 빼지 않는다.

### 4.1 쓰기와 안정화

- PostgreSQL 초기 적재는 COPY → CREATE INDEX → ANALYZE다. 증분은 **기존 HNSW를
  유지한 COPY**이며 wave당 한 트랜잭션이다. COPY의 전송 chunk를 논리 wave로 세지 않는다.
- Qdrant는 동결한 전송 batch 크기(1,000)로 동일 순서를 직렬 전송하고
  `wait=true` ACK를 기록한다. 한 논리 wave가 여러 HTTP 요청일 수 있다.
- M1/C1은 최종에만 안정화·검증·측정 장벽을 둔다. M5/C5는 매 wave마다 둔다.
- 실제 요청 수·건수·바이트·commit/ACK 시각·대기 시간·optimizer/segment 변화를 기록한다.
  일괄/분할 차이는 commit·중간 관찰·유지보수 기회까지 포함한 **경로 효과**다.
- 증분 구간에서 DROP/CREATE/REINDEX나 강제 전체 재구축은 금지한다. PG relation/index OID,
  Qdrant collection 동일성을 기록한다. Qdrant 내부 segment 재구성은 관측 대상이다.
- DB 자동 유지보수 설정을 기록·고정한다. 관측되지 않은 내부 삽입 순서나 PRNG까지
  동일하다고 가정하지 않는다. 네 경로 실행 순서는 seed별로 사전 무작위화한다.

### 4.2 fresh 대조군

| 대상 | 데이터셋·DB·seed 조합당 구축 | 전체 |
|---|---:|---:|
| 초기 D0 | 독립 fresh 3회 | 36 |
| 동일 최종 D0∪A | 독립 fresh 3회; 네 경로가 공유 | 36 |
| M5/C5 각각 wave 2·4의 상태 | 상태별 fresh 1회 | 48 |
| 합계 | 10회 | **120회** |

fresh는 같은 벡터·ID·속성·거리·M·efConstruction·검색 ef에서 새 인덱스를 만든다.
최종 세 번의 구축 입력 순서는 반복별로 미리 정한 셔플이다. backend 내부 난수는 별도
통제하지 못할 수 있다. fresh 간 범위를 보고하며, 이를 데이터 seed 반복과 구분한다.
중간 fresh 1회 결과는 진단이며 재구축 변동에 대한 확정 결론을 내리지 않는다.
wave 1·3에는 exact 정답과 inc 측정만 있으며 fresh 차이를 추정해 채우지 않는다.
같은 데이터 hash의 exact 정답은 재사용하지만 예정된 fresh 구축 반복은 생략하지 않는다.

## 5. 실험 수와 평가 질의 수

기본 조합은 2 데이터셋 × 2 DB × 3 seed = **12개**다.

| 항목 | 산식 | 수량 |
|---|---|---:|
| 초기 paired snapshot | 12 × 1 | 12 |
| 증분 이력 | 12 × 4 경로 | **48** |
| 증분 측정 | 12 × (M1 2 + M5 6 + C1 2 + C5 6) | **192** |
| fresh 구축·주 ef 측정 | 12 × (3 + 3 + 4) | **120** |
| 추가 ef 측정 | 최종 inc 48 × 2 + 최종 fresh 36 × 2 | **168** |
| 품질 측정 조건 합계 | 192 + 120 + 168 | **480** |
| 주 ef 증분 질의 | 144 × 200 + 48 × 600 | 57,600 |
| 주 ef fresh 질의 | 72 × 600 + 48 × 200 | 52,800 |
| 추가 ef 질의 | 168 × 600 | 100,800 |
| 평가 질의 합계 | 57,600 + 52,800 + 100,800 | **211,200** |

각 경로 복원 직후 초기 측정을 실제 수행하므로 네 초기 관측을 임의로 하나로 줄이지 않는다.
한 질의의 top-100 결과로 R@10과 R@100을 계산한다. 워밍업·튜닝·스모크·경로 검증용 추가
질의는 위 평가 질의 수 밖이지만 시간·자원 예산에는 포함한다. 이 수는 DAG node 수가 아니다.
48이력은 각각 1회 또는 5회 삽입이다. 50회 이력을 48번 수행하는 계획이 아니다.

## 6. 단계별 작업과 진입·종료 게이트

시간은 보장치가 아닌 최초 예약이다. 총 T0와 deadline은 고정하고 모든 작업이 공유한다.

| 단계 | 예약 | 작업 | 다음 단계로 가는 조건 |
|---|---:|---|---|
| S0 실행 준비 | 1.5h | 구조 개편 검증 인계, 새 실험 구현·설정·gate 검사, 버전 및 예산 고정 | G0: 승인 범위, 실행 경로, 고정 시계와 쓰기 경계 확인 |
| S1 데이터 준비 | 0.75h | 캐시 검증, holdout, 클러스터·event·oracle·cohort 생성 | G1: 입력·순서·최종 원장 동일성 및 정답 교차 검증 |
| S2 튜닝 | 1.5h | 별도 calibration 데이터에서 후보 구축·검색 ef 측정 | G2: 품질 목표와 비용의 적격 설정 동결 |
| S3 실제 스모크 | 0.75h | 양 DB·두 데이터셋의 실제 쓰기·복원·검색·실패 주입 및 비용 측정 | G3: HNSW 경로·원장·복구 검증, 전체 잔여 비용 수용 |
| S4 본 실험 | 5h | 48이력·120fresh·ef 측정, 셀별 상태 및 자원 감사 | G4: 모든 수량·hash·검색 경로·paired 조건 통과 |
| S5 분석·보고 | 1h | 대조 비교·집단별 분석·질의 CI·한계·정리·완료 감사 | G5: 원시 근거와 보고 일치, 12시간 내 제출 |
| 공통 예비 | 1.5h | 실패 진단·명시적 재시도·편차 | 별도 시작 시각이나 연장 기회를 만들지 않음 |
| 합계 | **12h** | 준비·수정·튜닝·대기·보고 포함 | 미완은 부분 결과로 남김 |

### G0 — 실행 전제

- 실제 실행 지시, 동결 spec/matrix/config hash, T0/deadline을 새 run에 기록한다.
- 구조 개편 후 import·CLI subprocess·DAG definition·source freeze·복원 검증이 통과해야 한다.
  G0에서 clustered CLI와 218개 native DAG 정의를 검증했다. 명령과 증거는 [실행 기록](clustered/execution.md)에 있다.
- G0에서 실제 `--help`, dry-run catalogue, 양 Python 환경 경로를 기록해 실행 명령을 확정한다.
- 기존 55개 실행 디렉터리와 docs/archive는 읽기 전용 입력이다. 과거 receipt 재생성 금지.
- 새 계획을 실행하는 소스만 새 snapshot에 동결한다. legacy hash 검사를 우회하지 않는다.
- 구조 개편 자체의 시간은 별도 작업이지만, 새 실험 전용 구현·검증은 S0/T0 안에 포함한다.
- 배치 크기·K·seed·질의 수·실험 수를 선언하고 기계 목록과 일치시키기 전에는 DB를 실행하지 않는다.

### G1 — 데이터와 oracle

- 입력과 cluster/event/질의 hash, calibration/evaluation 비중복, 원본 벡터 불변 확인.
- 4경로의 초기·최종 hash 일치, 두 1회/5회 쌍의 전체 순서 일치, 두 5회 경로의 wave 크기 일치.
- seed·데이터셋별 5개 비어 있지 않은 클러스터; 알고리즘·iteration·목적함수와 imbalance 기록.
- 현재 살아 있는 D_t만 대상으로 float64 block exact top-100을 계산한다.
  전체 최종 정답을 적재율로 보정하지 않는다. 동률은 점수 다음 ID로 결정한다.
- 상태마다 고정 표본 질의를 독립 scalar exact 구현과 대조한다. 결과 ID 중복·누락 검사를 수행한다.
- 변이 검사: ID 매핑 한 개 교체, 벡터 한 바이트 변경, 질의 순서 교체, 다른 상태 oracle 주입이
  각각 거부되어야 한다. 변이는 임시 사본에만 적용한다.

### G2 — 제한된 최적화와 동결

기존 선택값은 출발 후보이며 이번 calibration을 통과해야 한다.

| DB | 구축 후보 (M, efConstruction) | 검색 ef 후보 |
|---|---|---|
| pgvector | (16,100), (32,200) | 100,128,256,512,1000 |
| Qdrant | (48,300), (64,400) | 100,128,256,512,1000 |

두 데이터셋·두 DB별 후보 2개, 총 8개 구성 후보를 검사한다. 후보마다 초기, C5 wave 1·3·5,
최종 fresh의 5상태를 별도 calibration 입력으로 평가한다. 검색 ef별 200질의를 사용한다.
8 × 5상태 × 5 ef = 최대 200 calibration 측정 조건이다. fresh 초기 snapshot 구축·C5 변경 비용도 기록한다.

1. 5상태 모두 R@10/100 ≥0.99인 조합만 운영 후보가 된다.
2. 같은 적격 조합의 검색 p95·구축/삽입 시간·메모리를 기록한다. 다른 후보가 모든 비용에서
   같거나 더 좋고 하나 이상 엄격히 좋으면 지배된 후보로 표시한다.
3. 적격 비지배 후보 중 최악 상태 p95가 가장 낮은 조합을 선택한다. 5% 이내면 총 구축·삽입
   시간이 짧은 쪽, 다시 동률이면 M·efConstruction·ef의 사전식 순서로 고른다.
4. 적격 후보가 없거나 예약 시간을 초과하면 G2 실패다. 평가 결과를 보고 목표를 낮추거나
   후보를 무제한 늘리지 않는다. 변경은 새 계획 revision과 사용자 판단으로 처리한다.
5. 추가 ef 두 값은 위 오름차순 후보에서 운영 ef를 제외한 가장 작은 두 값으로 고정한다.
   운영 ef가 최소값이면 추가 값이 더 클 수 있다. 낮은 ef의 손실은 운영 품질 실패와 구분한다.

평가 입력을 튜닝에 쓰지 않는다. 대량 PG 적재의 COPY 경로, 전송 batch, builder 병렬도,
Qdrant optimizer·indexing 임계값도 calibration/스모크에서 검증하고 본 실험 중 고정한다.

### G3 — 실제 스모크, 검색 경로, 비용 입장

스모크는 평가 holdout과 분리한 calibration 입력에서 시행하고 본 실험 수에 합산하지 않는다.
양 데이터셋·양 DB에서 10K→20K C5 한 경로와 최종 fresh 한 번을 수행한다(총 4이력·4fresh).
같은 snapshot을 복원한 M1도 같은 4조합에서 시행해 단일 wave와 paired 복원을 검증한다.
합계 8이력·4fresh이며 작은 mock만으로 대체하지 않는다. 나머지 순서/경계 조합은 G1에서 전수 검증한다.

**PostgreSQL 경로 게이트**

- ANN 측정 세션마다 `enable_seqscan=off`, `enable_indexscan=on`을 설정하고 SHOW로 확인한다.
- 매 평가 SQL의 JSON EXPLAIN이 지정 HNSW index의 거리 ORDER BY 경로를 사용해야 한다.
  시점마다 대표 질의의 EXPLAIN ANALYZE도 남긴다. Seq Scan 또는 다른 인덱스 기반 정확 검색은 실패다.
- `seq_page_cost`, `random_page_cost`, CPU cost, cache 추정, parallel 및 iterative scan 설정을 기록한다.
  cost 조정이 필요하면 calibration 단계에서만 수행한다. cost 값 자체를 HNSW 실행 증거로 쓰지 않는다.
- [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/runtime-config-query.html)의
  설명대로 seqscan off는 절대적 실행 금지가 아니다. 따라서 계획 검사로 실패를 닫는다.
- 별도 임시 DB에서 HNSW 제거·seqscan on·다른 index plan 주입 각각을 검사가 거부해야 한다.
  exact oracle·원장 전수 확인용 scan은 ANN 질의와 분리한다.

**Qdrant 경로 게이트**

- `exact=false`, 동결한 `hnsw_ef`, full-scan/indexing 임계값과 index readiness를 기록한다.
- `wait=true` ACK만으로 인덱싱 완료를 판정하지 않는다. 전체 원장 검증과 optimizer 안정화 뒤 측정한다.
- 측정 전후 details_level=4 telemetry의 segment 식별자, HNSW/plain/exact 카운터를 대조한다.
  HNSW 사용, plain/exact 증가 0, 관측 구간 segment 안정성이 확인되어야 한다.
- telemetry 누락·segment 교체·혼합 검색이면 ANN-only PASS로 인정하지 않는다. 조용히 제외하지 않고
  원인과 시도를 보존한다. `indexed_only`로 미인덱싱 벡터를 숨긴 부분집합 결과도 허용하지 않는다.
- [공식 indexing 설명](https://qdrant.tech/documentation/manage-data/indexing/)에 따라
  full-scan threshold를 확인하되, 실제 의미는 동결 버전의 양성/음성 대조로 검증한다.
- 임시 컬렉션의 exact 요청, plain 검색, 누락 telemetry를 각각 검사가 거부해야 한다.

**시간·공간 입장**

- 스모크에서 source/oracle, COPY/요청, build, settle, restore, 측정, 검증, cleanup 시간을 분리한다.
- DB별 두 데이터셋의 더 느린 단가로 잔여 48이력·120fresh·168추가 ef의 전체 비용을 계산한다.
  1회/5회 경로는 별도 단가를 쓴다. 변동 추정이 부족하므로 1.5배 보수 계수를 적용한다.
- 남은 serial DB 비용 + 잔여 CPU/IO 비용 + 보고·정리 1h + 미소비 예비 시간을 합쳐 deadline
  안에 들어갈 때만 본 실험에 진입한다. 기존 12h 실험의 약 5h 관측을 이번 ETA로 대체하지 않는다.
- 예약을 포함한 peak disk와 RSS가 한도 안이어야 한다. 실패하면 본 실험을 시작하지 않고
  비용표와 미완 상태를 보고한다. seed/DB/fresh/질의를 자동으로 빼서 통과시키지 않는다.

### G4 — 본 실험 도중의 반복 게이트

모든 wave에서 ACK → 전체 원장 대조 → 안정화 → 현재 oracle·검색 경로 확인을 수행한다.
질의 중에는 설정 변경·쓰기·merge가 섞이지 않게 단일 측정 슬롯을 사용한다.
새 작업마다 남은 시간·공간을 다시 계산하고 현재 상태를 native receipt로 남긴다.

다음 조건이면 새 작업 입장을 중단한다: 입력/원장 불일치, 다른 검색 경로, source drift,
OOM·저장공간 경계 위반, 소유 자원 미정리, deadline 내 완료 불가능.
진행 중 쓰기의 결과가 불명확하면 자동 재전송하지 않는다. 상태를 먼저 읽어 확인하고,
복원이 필요하면 처음 snapshot에서 새 attempt로 시작한다. 실패 시도는 보존한다.
같은 셀에서 두 번째 실패 또는 같은 원인의 재발이면 반복 재시도를 멈추고 보고한다.

품질 저하 자체는 실험 실패가 아니다. 낮은 Recall을 이유로 조건을 제외하거나 튜닝을 바꾸지 않는다.

### G5 — 완료 감사와 제출

48이력, 192증분 측정, 120fresh, 168추가 ef, 480조건, 211,200평가 질의를 모두 센다.
원시 반환 ID/길이로 recall을 다시 계산하고, 보고서·원장·source/oracle hash를 검증한다.
모든 결과에 ANN-only qualification과 실행 시각을 붙인다. deadline 전 정리·제출이 완료되어야 한다.
숫자가 모자라거나 선행 gate가 실패했으면 전체 완료로 표시하지 않는다.

## 7. 지표와 판정

### 분리해서 보고할 값

- 시간 변화: 같은 200질의의 R_inc(t) − R_inc(0).
- 이력 차이: H(t)=R_inc(D_t) − mean(R_fresh(D_t)). 초기·최종은 fresh 3회, 지정 중간은 1회.
- 최종 순서 효과: C5−M5 및 C1−M1.
- 최종 분할 효과: C5−C1 및 M5−M1.
- 상호작용: (C5−C1)−(M5−M1). 클러스터 순서에서 분할 효과가 더 커지는지 본다.
- 주 지표 R@100, 보조 R@10; 질의 집단별 값, 짧은 결과·중복 ID, p50/p95/p99,
  구축·쓰기·안정화 비용, peak RSS/disk, 실제 segment/계획 증거.

고정된 운영 ef에서 history gap을 먼저 해석한다. 추가 ef 곡선은 같은 완성 인덱스에서
검색 설정만 바꾸며, fresh와 같은 ef로 비교한다. 높은 ef로 회복되더라도 그래프 구조가
정상이라는 증명은 아니다. 동일 recall에 필요한 탐색 비용 차이를 함께 보여준다.

### 반복·불확실성·탐지 한계

- 같은 seed·질의의 차이로 비교하고 질의를 대응 bootstrap 2,000회 재표집한다.
  데이터셋·DB·seed별 효과와 fresh 3회 범위를 먼저 제시한다.
- 질의 CI는 그 입력과 구축에 조건부다. 600×100 이웃을 독립 표본으로 세지 않는다.
- 주 확인 대비는 C5−M5와 상호작용이다. seed마다 두 대비 × 4 데이터셋/DB =8개이며
  세 seed까지 24개 조건부 주 대비를 한 family로 사전 등록한다. 유의성을 표현할 경우
  각각 bootstrap 양측 1−0.05/24 구간으로 보정하고 원래 95% 구간도 병기한다.
  보정 구간은 2,000회 표본으로 꼬리를 추정하지 않고 별도 고정 seed로 100,000회 계산한다.
  bootstrap block 크기를 제한해 메모리를 관리한다. 꼬리 추정이 불안정하면 보정 검정을
  확정하지 않고 탐색으로 표시한다. 조건부 질의 검정을 제품 일반화의 검정으로 바꾸지 않는다.
- 기본 조사 신호는 최종 C5의 fresh gap ≤−0.5%p와 C5−M5 ≤−0.5%p가 같은 DB/데이터셋의
  3 seed 중 2개 이상에서 함께 나타나는 경우다. 이는 후속 재현 우선순위이며 유의성 증명이 아니다.
- 계층 bootstrap 또는 seed간 효과 추정은 seed가 3개라 불안정할 수 있다. 평균·범위·부호를
  모두 보여주고 제품 전체에 대한 확정적 유의성이나 동등성을 주장하지 않는다.
- 데이터 준비 때 기존 calibration의 query 단위 변동으로 ±0.5%p 효과를 구분할 수 있을지
  진단한다. 표본이 부족하면 그대로 검출 한계로 적는다. 평가 결과를 본 뒤 표본을 바꾸지 않는다.
- 모든 ef에서 천장에 가까우면 “해당 탐색 예산과 표본에서 차이를 검출하지 못함”으로 쓴다.
  클러스터가 충분히 분리되지 않거나 질의가 해당 영역을 덮지 못한 경우도 함께 명시한다.

## 8. 로컬 자원, 병렬화와 DAG

2026-10-27 설계 시 `df -k .`의 Available은 38,575,784KiB(약 36.79GiB)였다.
이는 실행 입장 보장이 아니며 G0와 모든 예약에서 다시 확인한다.
원본 두 pool이 각각 100K×768×float32라면 벡터 값은 합계 약 586MiB다.
10K+10K 한 입력의 raw vector는 약 58.6MiB이고, 200×20K float64 점수 행렬은 약 30.5MiB다.
block exact와 memory map을 사용하고 동일 pool을 run별로 복제하지 않는다.
DB·WAL·JSON 전송·snapshot·원시 반환·로그 공간은 위 raw 크기로 추정하지 않고 스모크에서 잰다.

- 공유 cache는 hash를 확인해 읽기 전용 참조한다. 과거 source 캐시를 cleanup 대상으로 삼지 않는다.
- CPU-only 입력 준비는 최대 2 worker, DB 측정은 전역 1 slot이다. BLAS thread 수도 고정한다.
- CPU 준비·clustering·oracle 작업은 DB 측정 시작 전에 끝내는 것을 원칙으로 한다.
  본 측정 중 CPU 경쟁 작업을 병렬 실행해 지연 차이를 만들지 않는다.
- 같은 state의 oracle은 DB 간 공유한다. fresh는 선언한 구축 수만큼 실제로 각각 실행한다.
- 과거 사용한 just-dag-it/Dagster의 asset 의존성·입력 hash·완료 gate 구조를 활용한다.
  단순 subprocess 병렬 실행을 DAG 활용으로 간주하지 않는다.

논리 DAG: source 검증 → 분할·clustering → event/state/oracle → 튜닝 → 실제 스모크 →
비용 gate → 초기 snapshot → 48 histories 및 120 fresh → ef 조회 → 대응 분석 → 완료 감사.
DB 작업은 resource key로 직렬화하고, report는 전체 예상 catalogue와 성공 receipt에 의존한다.
bootstrap·정적 링크 감사 등 결과 전용 작업은 DB 종료 후 병렬화할 수 있다.

기한 직전 강제 종료로 증거가 손상되지 않도록, 신규 셀은 예상 실행+cleanup 시간이 남을 때만
입장시킨다. watchdog는 소유한 자원만 정리하고 원시 증거는 보존한다. 자동 prune은 하지 않는다.

## 9. 산출물, 승인 및 후속 확장

새 run에는 승인/동결 spec·config, source hash, 입력 row/cluster/event 매핑, oracle,
튜닝표, 비용표, native 상태, raw 검색 결과, 계획/telemetry, 분석표, 완료/정리 receipt를 둔다.
코드 정리 결과에 맞춘 실제 경로와 CLI는 G0에서 등록한다. 문서의 계획 JSON을 승인 없이
실행 설정으로 간주하거나 기존 12h 캠페인에 새 노드를 덧붙이지 않는다.

완료 기준은 G0~G5와 위 전수 수량이다. 보고서는 기존 합성 결과·이번 공개 벡터 관측·
원인 가설을 분리하며 “증분 인덱스는 열화되지 않는다” 같은 일반 명제를 쓰지 않는다.

기본 실험 이후 검토할 확장은 다음과 같다. **이번 480조건에는 포함하지 않으며 완료라고
보고하지 않는다.** 이 목록은 기존 전체 연구 범위를 폐기하는 결정이 아니다.
